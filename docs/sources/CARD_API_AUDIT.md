# 전체 카드 목록 API 감사와 요청 형식 진단

최신 범위 변경(C028)에 따라 아래 전역 전수 감사는 보존하는 조사/도구 이력이며, 현재 상점 공개·갱신의 무조건 선행 조건이 아니다. 과거 전체/전역/다른 버전 신규 확보는 보류하고 [현행 상품 대조](CURRENT_SHOP_COVERAGE.md)를 우선한다. 원래403 기록은 변경하지 않는다.

기존 R1/T002의 페이지네이션 조사와 R5의 전체 카드 확보 범위를, R4/T005 공개 전 실제 검증으로 보강하는 작업이다. 별도 로드맵 단계나 새 작업 ID를 만들지 않는다. 이번에는 **감사 도구와 49개 오프라인 fixture 검증을 완료했지만 실제 전체 수집은 첫 요청의 HTTP 403에서 중단됐다.** 요청 형식 진단 이후 추가 전체 감사 실행은 하지 않았다.

실제 결과는 [card-api-audit.json](../../data/research/card-api-audit.json)에 `status="blocked"`, `complete=false`로 기록했다. 기존 인수인계·초기 조사에서 출처가 보고한 **50,840개 카드·2,119쪽**을 전체 확보 결과로 바꾸지 않았다. 카드는 출시 카드/버전이며 실존 선수 50,840명을 의미하지 않는다.

## 실제 실행 결과와 비교 근거

감사 명령은 Node.js 24.19.0의 환경 프록시 지원으로 실행했다.

```bash
source /workspace/efsimulator-environment/activate.sh
node --use-env-proxy scripts/audit-cards.mjs --interval-ms 350 --request-budget 2300 --image-samples 30
```

이후 승인된 범위의 정상 HTML·해당 HTML이 실제 연결한 JS를 **각 1회**, 총 2회 읽었다. 둘 다 2026-10-25 05:06:22 UTC에 HTTP 200이었다. 감사 1회와 읽기 진단 2회를 구분해 기록했으며, 이 단계의 실제 HTTP 요청은 총 3회다. 진단에서 API나 이미지 요청을 추가하지 않았다.

현재 실제 JS의 요청은 다음 형태다.

```javascript
let e = searchParams.toString();
fetch(`/api/public/players${e ? `?${e}` : ""}`);
```

초기 페이지의 로컬 상태에는 `limit:24`가 있지만, 정상 `/ko/players`에는 쿼리가 없다. 페이지 이동 코드는 2쪽 이상에서 `page`만 추가한다. 따라서 정상 초기 조회는 `/api/public/players`, 다음은 `/api/public/players?page=2`이고, UI가 기본으로 `limit=24`나 `limit=100`을 붙이는 것은 아니다.

**403 하나로 모든 기본 목록 요청이나 전체 검증이 불가능하다고 결론내리지 않는다.** 이번에는 정상 기본 형식의 새 API 조회를 실행하지 않았으므로 현재 접근성은 미확인이다. limit100이 서버에서 지원되지 않는다고도 확정할 수 없다.

HTML에는 `__hub_req` 쿠키가 없을 때 `/api/auth/token`을 `credentials: 'include'`로 호출하는 부트스트랩 코드가 있다. 이번에는 코드를 읽기만 했고, 그 엔드포인트 호출·쿠키/토큰 획득·복사·재생은 하지 않았다. 이 코드만으로 403의 원인을 인증 조건이라고 확정하지 않는다. 헤더·프록시·TLS를 바꾸거나 다른 쿼리를 무작위로 시도하지 않았다.

## 구현한 감사 기준과 보존 방식

- 정상 API의 `players`, `total`, `page`, `limit`, `totalPages`를 검증하고 실제 반환 limit를 따른다. 명시적 정상 UI 모드 `--limit 24`는 1쪽에 쿼리를 넣지 않고 이후 `?page=n`만 사용한다. 기본 100 모드는 별도 크기 확인 요청이다. **403에서 다른 모드로 자동 전환하지 않는다.**
- 단일 동시성, 기본 요청 사이 최소 350ms, 실제 실행 최소 간격 250ms. 페이지·이미지·재시도를 고정 2,300회 예산에 포함한다. 첫 쪽·100쪽마다·마지막 쪽과 이미지 표본 처리 때 진행률을 출력한다.
- 정상 페이지 원문을 `artifacts/card-audit/pages/<page>.json`에 보존하고, 체크포인트의 SHA256·페이지별 행 수·관찰 시각과 대조한다. 긴 숫자·선행 0 카드 ID는 원본 문자열로 유지한다. 숫자 ID를 반올림한 다음 문자열로 만들지 않는다.
- 모든 페이지 존재, 페이지별 예상 행 수, 출처 총계의 중간 안정성, 마지막 쪽·잔여 행 수, 원본 ID 중복 0건, 고유 ID 수=출처 총계가 모두 맞아야 페이지네이션을 완료로 판정한다. 숫자 ID 간격으로 누락 카드를 만들어내지 않는다.
- 각 카드의 이름·HTTPS 이미지 URL·OVR·기본 분류 필드 존재 여부를 전수 집계한다. 실제 이미지 GET은 기본 30개를 `playerType`별로 나눠 표본 선정하고 HTTP 200·MIME·매직바이트·응답 바이트 수·해시를 확인한다. PNG 표본은 헤더 치수도 기록한다. 30개 표본을 전체 이미지 로딩 검증으로 표현하지 않는다.
- 단일 `playerType`, OVR 표시값, `imageUrl`만으로 복수 카드 분류·훈련/감독/부스터 적용 조건·배경/인물 분리·다른 버전 전체 연결을 확보했다고 판단하지 않는다. 목록에서 확보하는 행·필드는 전체 상세 스키마가 아니다.
- 403과 응답/코드 오류는 즉시 중단한다. 429·5xx만 최대 3회 재시도하며 각 대기는 60초 이하로 제한한다. 더 긴 `Retry-After`, 재시도 소진 또는 요청 예산 소진은 `paused`로 저장한다.
- `paused` 재개는 성공한 페이지의 해시와 계약을 재검증하고 완료 페이지를 다시 받지 않는다. raw 파일 저장 직후 체크포인트 등록 전 중단된 경우에는 새 정상 응답과 기존 raw의 해시가 같을 때만 원본을 유지해 등록한다. 다르면 기존 파일을 보존하고 중단한다.
- 재개 전에 요청 수의 비음수 정수 여부·로그 길이 일치, 허용 상태, 요청 로그의 URL·종류·페이지·시각, 페이지 번호 연속성·다음 페이지·총계/limit·페이지 메타데이터와 성공 요청의 대응을 검증한다. 손상은 네트워크·파일 쓰기 전에 `invalid_checkpoint`로 거부한다. 손상된 state를 자동 보정하거나 기존 정상 요약·raw·진단 요약을 덮어쓰지 않는다. 파일에 저장된 `null`·기타 원시값도 없는 파일로 취급하지 않는다.
- 정상적인 응답 직후에는 200 요청 로그만 있고 총계·limit는 아직 `null`, 등록 페이지는 없을 수 있다. 이 중단 상태와 등록 전 raw 파일은 정상 재개 대상으로 유지한다. 이미 사용한 요청 수보다 새 예산을 작게 지정하면 손상으로 판단하지 않고 추가 요청 없이 `paused`로 남긴다. 빈 200 본문 때문에 저장된 `response_bytes=0` 또는 `valid=false, bytes=0` 이미지 결과는 정상적인 차단 기록이며 재개 시 재요청하지 않는다.
- `blocked`인 403 체크포인트를 `--resume`으로 실행해도 네트워크 재시도를 하지 않는다. 재개 중 요청 모드도 바꾸지 않는다. 실패한 실행은 기존 `complete=true` 요약을 덮어쓰지 않으며 진단용 불완전 결과를 별도 artifact에 남긴다.

요약의 `complete`는 **관측한 카드 목록의 전수 열거와 설정한 이미지 표본 검증**을 뜻한다. 모든 상세 필드·모든 게임 자료·모든 실존 선수·전 이미지의 완전성을 뜻하지 않는다. 이름·이미지 URL 등이 부족하면 그 수량을 별도로 확인해야 한다. 현재 실제 요약은 초기 응답 거부로 페이지네이션·이미지 표본 모두 미완료다.

## 검증과 현재 후속 상태

`node --test tests/audit-cards.test.mjs`로 **49개 fixture가 통과**했다. 실제 외부 요청을 하지 않는 테스트이며 다음을 검사한다.

- 전체 쪽·마지막 행·고유 ID 대조, 긴 문자열/선행 0 유지, 중복·총계 변경·누락 거부.
- 응답이 limit100을 무시했을 때 실제 24 기준 사용, 정상 UI 모드의 정확한 쿼리 형식.
- 초기/중간 403 중단과 정상 요약 보존, 관측 0건을 이미지·총계 안정성 완료로 잘못 표시하지 않음.
- 체크포인트 해시 변조, 예산 재개, raw 파일 저장 직후 중단·충돌, 503 한정 복구/재시도 소진과 긴 Retry-After 중단.
- 서로 다른 카드 유형의 이미지 GET 표본, MIME/실제 본문이 다른 가짜 이미지 거부.
- 음수/비정수 요청 수·로그 불일치·페이지 건너뜀/되감기·잘못된 상태와 메타데이터, 부분 페이지의 거짓 완료 상태 거부 및 모든 기존 파일 바이트 보존.
- 정상 200 로그 직후의 총계 미확정 중단 상태, 낮춘 요청 예산의 무요청 일시정지, 빈 200 본문의 차단 기록, `null`·다른 원시값 state 거부.

오프라인 재개 검증 보강에서는 요청 수를 `-5`로 바꾸면 예산 1에서도 추가 mock 2회 후 요청 수 `-3`·로그 길이 3으로 완료되는 문제를 먼저 재현했다. 메타데이터 사전 검증으로 이 경로를 차단하고, 손상 state·기존 정상 요약·raw·진단 요약의 바이트 보존과 정상 중단 재개를 함께 검사한다. 이 수정은 실제 403 관측·실제 체크포인트·감사 JSON을 바꾸거나 외부 요청을 실행하는 작업이 아니다.

`--limit 24` 선택 모드는 구현·fixture 검증만 완료했다. 별도 실제 실행 승인은 이후 철회되어 **두 번째 live 감사는 시작하지 않았다**. 추가 API·이미지 요청은 멈춘 상태이며 새 쿠키·토큰·서비스·비용 권한도 요구하지 않는다.

기존 403 기록과 정상 UI 요청 형식의 차이를 유지한 채, 전체 검증은 **차단 상태의 미완료 선행 작업**으로 남긴다. 이후 실행 여부가 정해지더라도 원래 403 기록을 보존하고 실제로 확인한 범위만 보고한다. 생산 seed·앱 DB·검색 공개 데이터에는 자동 병합하지 않았다.
