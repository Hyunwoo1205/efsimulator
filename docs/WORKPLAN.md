# efsimulator 작업 계획과 이력

최신 사용자 결정에 따라 전체 누적 EFHub DB/API와 공식 KR 현재 판매 사이트 DB를 분리한다. T022 이관 뒤 T023에서 별도 API Sites 소스·schema·로컬 수입/연동 준비를 완료했다. 과거 관측·완료 이력은 보존하며 새 구현 완료로 승격하지 않는다.

## 현재 작업과 매 작업 갱신

- 이전 작업: T027 — 엄격 검사·증거 재실행·결정적 갱신·규칙 변경 통제 완료.
- 현재 작업: T025 — 예정. 미확정 3상품 관계와 실제 API Site/D1 검토 배포 검증.
- 다음 작업: T011 — 검토된 관계·스키마·수입 범위 보완.
- 현재 조건: raw 47,408선수/1,699팩 보존. 공식7상품 관측 중4팩44카드 가공·live4/archive0 검증, 나머지3 관계 대기. 과거 EFHub HTML403 이후 T026에서 정상HTML200과 기존44카드 관계 재검증, 신규 원본 추가0건. 매시간 점검 예약 활성, 실제 Sites/원격D1 배포 미실행. 작업 기준은 api-server-setup 브랜치와 services/catalog-api.

매 작업 시작 시 Git 상태·이전 결과·이번/다음 작업·선행 조건을 확인한다. FILE_SYNC의 P0→P1→P2로 관련 파일을 검토하되 필요한 파일은 등급과 무관하게 함께 수정한다. 추가 요구는 ID·영향 단계·선행 조건·순서·상태를 기록한다. 파일별 수정/변경불필요/미해결과 근거, 경로 추가/삭제/이름 변경·참조를 같은 작업에서 갱신한다. 검증과 이전/현재/다음 포인터를 맞추며 구현/수집/발행 완료는 실제 근거가 있을 때만 표시한다.

## T009 — 후보 API 검증과 최종 선정

- 단계: R1
- 상태: 차단
- 이전: T019
- 다음: T010

### 목표·입력·순서

입력: 최신 공식 기준표, API_SELECTION, 기존 저장 응답·권한/오류 기록.

1. 정상 허용 경로·자동 접근·저장/재배포 조건·쿼터와 비용부터 확인한다. 부족하면 필요한 정확한 공급자 조건을 기록한다.
2. 당시 공식 대상 각각의 회차와 모든 특수 종류의 manifest를 대조한다. 현재 부족한 National/Quaresma/Midfielders 근거를 먼저 보강한다.
3. 선정 시험용 비활성 수집으로 모든 특수 카드의 필드와 이미지 실제 로드→디코딩→허용 저장→재읽기·해시·카드 연결을 검증한다.
4. 안정적인 최신 발견 방식과 실제 공급자 변경 전후·오류/축소 보호·어댑터 계약을 확인하고 모든 필수 게이트가 통과한 뒤 최종 선정한다.

### 산출물·검증·완료 조건

정확 URL/메서드/쿼리·시각/해시·상품별 회차/전체 특수ID·중복/unknown·이미지 전수 결과·권한·갱신 전후·예상 비용과 선정 보고서를 남긴다. 필수 게이트 하나라도 미통과이면 최종 선정/작업 완료 금지다.

### 선행 조건·보류 사항

사용자 실행 승인으로 착수했다. 이미 거부된 요청을 반복·변형하지 않는다. 연락·추가 권한·유료 계약이 필요하면 최소 조치와 근거를 제시한다. 시험 자료는 DB/활성 import가 아니며 T010에서 재사용한다.

### 예상 영향 파일

docs/API_SELECTION.md, 공식 기준표/선정 검증 기록, ROADMAP/WORKPLAN/FILE_SYNC. 새 검증 기록은 추가 즉시 등록한다. 신규 파일의 경로/역할·연관 파일은 착수 때 확정하고 추가와 동시에 FILE_SYNC에 등록한다.

## T010 — 보유 raw 재사용·팩 상세와 카드 관계 검증·수입 준비

- 단계: R2
- 상태: 진행 중
- 이전: T023
- 다음: T011

### 목표·입력·순서

입력은 검사한 players/packs 원본과 해시, 빈 필드·의심 항목 보고, 기존 Work의 상세·관계 자료와 T022 이관 확인서다. T022에서 기존 9팩·79관계의 모든 slug/card ID가 양쪽 raw에 존재함을 확인했으며 공식 회차·특수 집합 완전성은 별도 검증한다. 두 raw를 다시 수집하는 것으로 시작하지 않는다.

1. 기존 대상 Work에 팩 상세·카드 명단·원본 ID 관계 자료가 이미 있는지 먼저 확인한다. 팩 목록의 네 필드만으로 관계를 추측하거나 playerCount 합계를 실제 구성 수로 사용하지 않는다.
2. 없는 관계는 허용된 정상 상세 API·HTML 등의 출처에서 정확한 팩 회차와 카드 ID 근거를 확보할 계획을 세운다. 기존 접근 제한 우회·거부 요청 반복·이름만으로 연결은 금지한다. 실제 요청은 해당 작업 착수 범위에서 수행한다.
3. 팩 회차→카드 ID manifest의 출처·관측 시각·명단 범위·중복·고아 참조·특수 집합 완전성을 검증한다. 모든 과거 팩 관계의 완성을 최초 DB 설계의 새 선행 조건으로 만들지 않으며 미확인 관계는 상태로 보존한다.
4. 빈 name/slug와 dummy 의심 항목을 원본 삭제 없이 정규화·공개 격리 검토 대상으로 정리하고, 실제 필드·관계·ID·개정·무삭제 요구를 T011 설계 입력으로 전달한다. 실제 DB 수입은 스키마 계약을 확정한 뒤 T011에서 진행한다.

### 산출물·검증·완료 조건

기존 자료 재사용 목록, 검증된 관계 manifest의 범위·미확인 상태, 격리 검토 목록, 정규화 설계 입력이 필요하다. 선수·팩 배열의 내부 검사와 상품 구성·공식 전체 풀 완전성을 구분한다. 원본을 변경하거나 새 DB에 즉시 편입하지 않는다.

### 선행 조건·보류 사항

T021의 파일 내부 검사와 한계 보고는 완료됐다. 정상 제공·이용 조건은 해당 처리별로 확인하며 누적 원본 보존과 공개 권리를 구분한다. T023에서 최신 raw 검증·10팩/90관계·독립 API/staging 준비를 재사용한다. 원출처 새 요청·공식 회차/전체 특수 검증과 전체 T010 완료는 별도다.

### 예상 영향 파일

## T021 — 제공 players raw 검증과 packs·관계 입력 확인

- 단계: R1
- 상태: 완료
- 이전: T020
- 다음: T022

### 입력과 실제 결과

상위 채팅의 검증 환경에서 Library의 players_raw.json v1(libfile_cc5085f5c4788191b7c3707a66e0529a)을 가져와 오프라인 검증한 결과를 전달받았다. 원본 수정과 EFHub·이미지 요청은 없었다. 이 실행 환경의 Library 도구 부재와 검증 환경의 성공을 구분한다.

- 실제 크기는 16,801,176 bytes이며 SHA-256은 `16b5ac4919480bbbf8e5158946322fac1f406f0d66701c4d52c9274107dc94c4`다.
- 유효 JSON 최상위 배열이다. 카드 객체와 고유 십진수 문자열 ID는 각각 47,397개이며 중복 ID, 충돌 중복, 중복 JSON 키는 모두 0개다. 최대 ID는 `387113187158919`이며 안전 정수 범위 안이지만 문자열을 유지한다.
- `name`, `imageUrl`, `overallRating`, `playerType`은 모두 존재하고 null·빈 값이 아니다. OVR은 정수 40~102, 타입은 정수 1~8이다. OVR 조건과 타입명 매핑은 미검증이다.
- `nationality`와 `nationalityCode`는 전부 빈 문자열이며 `nameZh`는 795개 항목에서 빈 문자열이다. `playingStyle`은 7,927개, `playingStyleDefensive`는 42,561개 항목에 없다.
- 페이지, 커서, 출처, 수집 시각, total 메타는 없다. 원래 페이지의 완전성·현재성, 팩 관계, 이미지 실제 로드는 별도 미검증이다.

### 팩 raw 추가 검사 결과

사용자의 제작 완료 보고 뒤 상위 환경에서 Library packs_raw.json을 실제 오프라인 검사했다. 검색 버전 메타는 null이었으며 materialize 결과 current_version_number는 0이다. 팩 파일을 v1로 표기하지 않는다.

- Library ID는 `libfile_467e20cb94a8819195dba5375e7e013a`, File Service ID는 `file_00000000be188206896993ce4d932193`다. 실제 크기는 197,874 bytes이며 SHA-256은 `bfe4590cfa5acb18106a98206b9acad71616f2622cf0d44ae3257040a56b97d6`이다.
- 유효 JSON 배열에 객체 1,699개가 있다. 모든 항목에는 name·slug·date·playerCount 네 필드만 있다. 고유 slug 1,699개에는 빈 값 1개가 포함되며 비어 있지 않은 고유 slug는 1,698개다. 빈 name은 1개이고 중복 slug·충돌 중복·중복 JSON 키는 0개다.
- name·slug·date는 문자열, playerCount는 정수다. 날짜 범위는 2022-04-01~2026-10-26이며 잘못된 날짜는 없다. 날짜가 수집 시각이라는 뜻은 아니다. playerCount는 1~48이고 합계 12,946은 원본 선언값의 합계일 뿐 실제 구성·고유 선수·공식 풀 크기가 아니다.
- 0부터 세는 배열 인덱스 99의 name/slug는 dummy, date는 2026-07-23, playerCount는 33이다. placeholder 의심으로 원본을 보존하고 정규화·공개 단계에서 격리 검토한다. 빈 name/slug도 원본 삭제 없이 검증 보고·격리 검토 대상으로 둔다.
- pack ID, card ID, 선수 명단·중첩 배열, 팩 이미지는 없다. 두 raw만으로 관계 조인은 불가능하며 이름으로 추측 연결하지 않았다. 페이지·커서·수집 시각·total 메타도 없다. 원본 수정과 EFHub·이미지 요청은 0회이며 선수 raw의 기존 SHA도 동일함을 재확인했다.

### 다음 순서와 보류 사항

1. 이전 50,840개와 현재 47,397개의 차이인 3,443개는 사용자 설명상 중복 제거 결과다. 현재 파일의 고유 ID·중복 0개 검사와 원본 중복 제거 로그 검증은 별개이며 후자는 재검증하지 않았다. 누락 의심을 주요 차단 요인으로 삼거나 전체를 재수집하지 않는다. 기존 대상 Work의 출력과 체크포인트를 이어받는다.
2. 양쪽 raw를 재사용하고 기존 대상 Work에 팩 상세·관계 자료가 이미 있는지 먼저 확인한다. 새 채팅이나 중복 수집을 시작하지 않는다. 팩 회차·특수 명단·card ID 관계 확보는 T010, 스키마 확정 후 실제 수입은 T011로 이어간다.
3. 이미지 URL 존재와 실제 로드·허용 저장·재읽기를 구분한다. 이번에는 이미지 다운로드, 새 DB/API, 자동화, main 병합, 배포 설정 변경을 실행하지 않는다. 최신 사용자 승인으로 work 정상 푸시와 기존 CI·연결된 preview 확인만 허용됐다.
4. 양쪽 파일의 검사 결과와 관계 미확인 상태를 구분하고 T010의 수입 준비 계획을 따른다. 이 실행 환경에는 Library 업로드 도구가 없으므로 인수인계 MD 저장은 상위 채팅의 지원 환경에서 진행한다.

### 완료 조건과 검증 범위

양쪽 파일의 내부 검사와 현재 관계 자료의 한계 보고를 마쳐 T021을 완료했다. 빈 식별 필드·의심 항목이 모두 정상 데이터라는 뜻이나 원래 페이지·현재성·팩 구성 완전성을 검증했다는 뜻은 아니다. 팩 상세·카드 관계 근거와 정규화 설계는 T010→T011에서 진행한다. 이번 저장소 변경은 검증 결과와 현재 상태, 인수인계 문서 반영이다. 코드·테스트·활성 자료·원래 관측은 보존한다.

### 검증과 원격 반영

이전 T020·선수 raw 반영·교정 이력은 보존한다. 이번 팩 검사 결과 반영에서도 테스트 224개, 관리 파일 79개·작업 22개·변경 경로 13개, 기존 표본 빌드, 공개 파일 7개 비교, 상대 링크 151개, diff 검사를 통과했다. 코드·테스트·활성 자료·원래 관측은 기준 커밋 116fb19와 같다. UI 변경이 없어 브라우저 검사는 다시 실행하지 않았다.

사용자 승인에 따라 문서 갱신을 work에 정상 푸시하고 최종 원격 SHA와 CI를 최종 보고·receipt에 기록한다. main 병합·배포 설정 변경·새 자동화는 하지 않으며 기존 CI·preview 트리거를 운영 병합으로 간주하지 않는다.

### 예상 영향과 검증

services/catalog-api의 신규 source/lock/migration/client/수입 스크립트·테스트·README, 관리·아키텍처·배포 문서를 함께 등록한다. node 테스트·기존 앱 회귀·project:check·원격 SHA를 검증하고 상세 파일 판정은 종료 시 작성한다. 단순 입력 총계나 로컬 성공을 현재 판매/공식 회차·전체 특수 검증이나 hosted API 운영 성공으로 표시하지 않는다.

### 실제 결과·검증·완료 범위

API 전용 source/5테이블 schema·generated SQL/메타·GET client·정규화/초기 수입·export를 준비했다. 실제 입력은 카드 47,408·유효팩 1,697·quarantine 2·10팩/90관계다. staging 수입/replay·고아 참조 0과 실제6개 경로 응답을 확인했다. 테스트 245개(신규 API 21개), TypeScript·공식 Sites build, 기존 앱 build/Pages7 비교를 통과했다. live 원자적 갱신·현재 공식 projection·hosted DB·계정 비용/백업·실제 사이트 연결은 미완료로 범위를 분리한다. 새 브랜치의 정상 push는 이 사용자 요청 범위에 포함하고 main/work·기존 앱·실제 Sites 배포는 변경하지 않는다.

## T024 — HTML 누적 수집·가공 DB·전체 live/archive·갱신 로그

- 단계: R2
- 상태: 진행 중
- 이전: T023
- 다음: T025

최신 사용자 C056~C059를 구현한다. 새 관계가 검증된 공식 상품만 가공하며 기존 raw를 보존한다. 상세 계약은 [CATALOG_DATA_CONTRACT](CATALOG_DATA_CONTRACT.md). EFHub 수집기 HTML403은 실패 보호로 처리하고 신규 수입 성공으로 보고하지 않는다. 기존 자료와 현재 공식 관측으로 검증 가능한 4팩·44카드 표본을 사용하며 미확정 3상품은 대기한다. 실제 Site 배포·원격 D1 적재는 미실행. 로컬 가공 발행 44선수/4팩/live4/archive0과 실제 API 7경로200을 확인했다. 전체 Node 테스트312개·TypeScript·공식 Sites Worker 빌드 통과. 이후 run-cycle 통합3개를 마지막 정리 후 다시 통과했다. 공식 상품7 중3은 관계 미확정이며 HTML403으로 신규 raw 추가0건이다.

검증 데이터 묶음은 catalog-api-lifecycle-data.tar.gz로 저장했다. 매시간 조건 점검 예약을 Asia/Seoul 기준으로 활성화했으며 첫 예약 실행의 수집·수정 성공은 아직 관측하지 않았다. 현재의 수집기403과 미확정3상품을 예약 등록으로 해결했다고 표시하지 않는다. 원본 API 호출0회, 새 원본 수집0건이며 제공된 raw와 기존 관계를 재사용했다.
