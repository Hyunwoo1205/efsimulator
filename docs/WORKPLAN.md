## T002 — R1 출처·수집 가능성 검증

- 단계: R1
- 상태: 완료
- 이전: T001
- 다음: T003

### 목표

실제 접근 가능한 출처와 확보 가능한 현행·과거 데이터의 범위를 확인하고, 필수 필드와 전체 구성을 입증할 수 있는 수집 근거를 확보합니다.

### 순서

1. [EFHub 한국어](https://efhub.com/ko), [EFHub 원문](https://efhub.com), [공식 eFootball](https://www.konami.com/efootball/)의 실제 응답·목록·상세·정상 요청을 확인합니다.
2. 선수 카드·감독·상품의 외부 ID와 실제 제공 필드, 이미지 참조와 합성/분리 형태를 표본으로 기록합니다. 과거 선수 API 경로는 재검증하고 감독·상품 경로를 추측하지 않습니다.
3. 전체 목록·페이지네이션을 확인하고 대표 목록과 전체 구성의 차이, 명단 인원수와 확보 카드 수를 대조합니다.
4. 상품별 구성·가격·재화·1회/복수회 옵션·이용 제한·기간·상태의 근거를 기록합니다. 비코인 상품과 감독도 포함합니다.
5. 필드별 출처 URL·원본 문자열 ID·관찰 시각·원문 근거와 확보/미확인을 정리합니다. 현행 범위, 확보 가능한 과거 범위와 실제 갱신의 관찰 방법을 분리합니다.
6. 데이터 공백·접근 제약·전체성 제약과 R2의 기술 선택에 필요한 규모·처리 예산을 정리합니다.

### 검증

- 실제 HTTPS GET 27회(200 26회, 403 1회), 상품 2쪽·선수 목록 2쪽과 상세 payload·이미지 메타를 확인했습니다.

## T004 — R3 실제 표본의 DB·검색 전체 흐름 검증

- 단계: R3
- 상태: 완료
- 이전: T003
- 다음: T005

### 목표

검증한 조사 표본을 SQLite와 정적 검색 화면으로 연결하고 부분 확보·미확인·출처를 표시합니다. 이전 감독 관계 필수 기준은 최신 사용자 범위 변경으로 폐기했습니다. 아래 초기 구현 기록과 최종 지원 범위를 구별합니다.

### 초기 순서와 구현 결과 (범위 변경 이전 기록)

1. `npm run data:prepare`로 원본 조사 증거에서 상품 1개·카드 15개·감독 1명을 재현합니다. 내부 ID는 출처·종류·원본 문자열로 결정하고 관측 ID는 시각·응답 해시를 포함해 새 관측과 기존 관측을 구분합니다.
2. 검증→SQLite 저장→정적 JSON→한국어 검색·상세를 연결했습니다. 상품↔카드·다른 버전·감독 별도 탐색과 필터·URL·뒤로 이동을 구현했습니다.
3. 미확인 가격·재화·전체 선수 수·상품 감독·이미지 분리 형태·능력치 조건은 미확인으로 유지했습니다. 출처 목록 총계는 확보 수량과 구분합니다.
4. 정상 관측도 종류·원본 ID가 다른 상품 구성의 근거로 쓸 수 없게 보강하고, 전체 인원·완전성에는 별도 상품 상세 근거를 요구했습니다.
5. Pages에는 top-level 404와 실제 목록·상세 경로 rewrite만 생성해 없는 JSON이 HTML 200으로 바뀌지 않게 했습니다. CI에 실제 표본 재현·JS 문법·정적 빌드 검사를 추가했습니다.
6. 후속 공식·플랫폼 출처 10회 관측을 별도 증거로 기록했습니다. Daily Free Draw의 무료 1일 1회와 PS 한국 현금 번들 28,000 KRW를 현재 표본의 가격·조건으로 옮기지 않았습니다.

## T005 — R4 현행 범위 확장·전체 API 검증·부분 공개 배포

- 단계: R4
- 상태: 진행 중
- 이전: T004
- 다음: T006

### 목표

현재 확보 가능한 카드·상품을 확장하고, 감독 지원 범위를 일관되게 적용한 부분 검색 사이트와 기존 무료 Pages 배포를 검증합니다. 전체 API 전수 검증은 기존 R1/T002와 R5의 범위를 이 작업의 선행 진단으로 보강하며 별도 중복 작업을 만들지 않습니다.

### 순서와 실제 결과

1. 정상 EFHub 상품 API와 같은 제목·표시 수·직속 구성 grid를 수집하고 Flight와 본문 카드 ID를 대조했습니다. 첫 상품의 지연 JSON 참조 때문에 중단된 파서를 정확한 참조 범위만 해석하도록 보완했습니다. 수집 실패는 기존 자료를 보존했습니다.
2. 1상품/2요청 검증 후 9상품/10요청으로 확대했습니다. 활성 자료는 상품 9개·카드 83개입니다. 원본 ID·출처·필드 조건·다른 버전 근거를 보존하고 이름 병합은 하지 않았습니다.
3. 최신 범위 정책으로 managers=[]와 manager 구성 거부를 적용합니다. 일반 감독 목록과 개별 기사·화면은 상품 일괄 API를 대신하지 않습니다. 옛 수동 코드·테스트는 docs/reference 텍스트로 보존했고 활성 import/test에서 제외했습니다. 이전 생성 DB/사이트는 artifacts/scope-change-20261025-manager-exclusion에 보존한 뒤 명시적 범위 변경으로 재빌드했습니다.
4. 전체 카드 감사 도구에 체크포인트·해시·고유 ID·중복/누락·마지막 페이지·총계 변동·이미지 필드/실로드 표본·백오프·403 즉시 중단을 구현했습니다. 실제 첫 GET /api/public/players?page=1&limit=100은 403, 확보 0쪽·0카드·이미지 0건입니다.
5. 과거 정상 GET /api/public/players 및 ?page=2(24개)와 현재 정상 UI/JS가 쓰는 초기 무쿼리·다음 ?page=n을 비교했습니다. 정상 UI/JS 2회 진단 외 추가 API·이미지 요청은 하지 않았습니다. --limit 24 형식은 코드/fixture로만 검증했고 실제 재시도하지 않았습니다. limit100 지원 여부와 전체 데이터 접근 가능성은 미확인입니다.
6. 기존 Cloudflare root 정적 배포와 호환되는 7개 공개 파일을 dist에서 생성합니다. 새 인증을 사용하거나 현재 대시보드 설정을 읽었다고 주장하지 않습니다. CI는 fresh build 후 원본/생성물 bytes 차이에 실패하며 자동 갱신하지 않습니다.
7. 로컬 검증을 마친 브랜치의 기존 Git 연동 미리보기·CI와 공개 응답을 검증합니다. 원격 쓰기·배포 결과는 실제 실행 후 기록합니다. 차단된 전수 API 검증을 성공으로 표현하지 않고 검증 범위를 표시한 부분 공개만 진행합니다.

### 검증

- 고정 Node 24.19.0·npm 11.9.0에서 npm ci, data:prepare, build 통과. 활성 상품 9개·카드 83개이며 모든 감독 데이터·관계는 지원 범위에서 제외했습니다.

- 실제 Chromium 브라우저 **7개 묶음 통과**, pageerror 0. 모든 9상품에서 감독 미지원·부분 구성 표시, 상품↔카드·버전·검색·직접 주소·뒤로 이동·빈 결과·실패/재시도·이미지 대체와 768/390/320px 넘침 없음을 확인했습니다.
- pages:export 후 pages:check 통과: 고정 7개 파일의 dist/root bytes 일치. project:check --base d8891f2 통과: 파일 55개·작업 8개·변경 경로 55개. JS 문법·git diff --check 통과.
- 전체 API 감사의 실제 결과는 data/research/card-api-audit.json과 CARD_API_AUDIT 문서를 기준으로 합니다. 실제 1요청403·0페이지·0카드·이미지0이며 진단2GET와 fixture 성공을 전수 수집 성공으로 표현하지 않습니다.
- 신규 파일까지 포함한 git diff --cached --check에서 문서 끝의 추가 빈 줄 4건을 발견해 정리했습니다. 제품 코드·원문 관측은 변경하지 않았습니다.

## T006 — R5 허용된 과거 자료·전체 카드 확장

- 단계: R5
- 상태: 예정
- 이전: T005
- 다음: T007

### 목표와 순서

전체 카드 API 감사는 T005에서 기존 R1/T002 범위로 먼저 진단합니다. 여기서는 허용된 수집 경로와 실제 검증 결과에 따라 과거 상품·카드의 DB/검색 반영과 규모·성능·분할·누락을 확장합니다. 차단된 요청을 새 작업으로 반복하지 않습니다.

### 검증과 완료조건

출처 범위·고유 카드 ID·중복·누락·원문 필드·이미지 표본/전수 구분·버전/관계·검색 성능을 대조하고 부분 확보와 전체 완료를 구분합니다. 감독 지원 제외와 팩/추첨 구분을 유지합니다.

### 추가조건

R4의 전수 미검증/접근 제약을 먼저 확인합니다. 출처가 허용한 데이터 피드/내보내기 또는 정상 접근 근거가 확보되기 전 추가 우회 수집을 하지 않습니다.

## T007 — R6 지속 갱신 운영 검증

- 단계: R6
- 상태: 예정
- 이전: T006
- 다음: 없음

### 목표와 순서

실제 신규 자료·조건 변경이 수집→검증→저장→공개로 반영되는 전후 근거와 실패 시 정상 자료 보존을 확인합니다. 반복 조회나 fixture 성공만으로 지속 갱신을 완료 처리하지 않습니다.

### 검증과 완료조건

실제 자료 변화·처리 예산·실행 기록·이력 영속화·복구를 확인합니다. 새 자격 증명·지속 접근·예상하지 못한 권한·유료 비용이 필요하면 대상과 최소 필요 사항을 먼저 제시합니다.

### 추가조건

DB·전체 검색·갱신 완료 전 시뮬레이터 구현은 시작하지 않습니다. 향후 대상은 코인 기반 특수 선수 명단이며 모든 일괄 지급형 팩은 제외합니다.
