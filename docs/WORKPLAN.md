## T002 — R1 출처·수집 가능성 검증

- 단계: R1
- 상태: 완료
- 이전: T001

### 목표

### 순서

1. [EFHub 한국어](https://efhub.com/ko), [EFHub 원문](https://efhub.com), [공식 eFootball](https://www.konami.com/efootball/)의 실제 응답·목록·상세·정상 요청을 확인합니다.
2. 선수 카드·감독·상품의 외부 ID와 실제 제공 필드, 이미지 참조와 합성/분리 형태를 표본으로 기록합니다. 과거 선수 API 경로는 재검증하고 감독·상품 경로를 추측하지 않습니다.
3. 전체 목록·페이지네이션을 확인하고 대표 목록과 전체 구성의 차이, 명단 인원수와 확보 카드 수를 대조합니다.
4. 상품별 구성·가격·재화·1회/복수회 옵션·이용 제한·기간·상태의 근거를 기록합니다. 비코인 상품과 감독도 포함합니다.
5. 필드별 출처 URL·원본 문자열 ID·관찰 시각·원문 근거와 확보/미확인을 정리합니다. 현행 범위, 확보 가능한 과거 범위와 실제 갱신의 관찰 방법을 분리합니다.
6. 데이터 공백·접근 제약·전체성 제약과 R2의 기술 선택에 필요한 규모·처리 예산을 정리합니다.

### 검증

- 실제 HTTPS GET 27회(200 26회, 403 1회), 상품 2쪽·선수 목록 2쪽과 상세 payload·이미지 메타를 확인했습니다.
- 출처 보고 총계는 상품 1,698개·카드 50,840개이며 수집 완료 수가 아닙니다. 표본 상품의 카드 11개, 다른 버전 3개, 감독 1명을 확인했습니다.
- JSON 구조·관찰 ID·문자열 source_ids·11개 고유 카드·타입 매핑·이미지 메타·참조 무결성 검사 통과. 결과는 출처 조사 문서와 증거 JSON에 기록했습니다.
- 구조 조사 완료이며 데이터 완전성·실제 지속 갱신은 완료로 선언하지 않습니다.
- 실제 카드·상품·감독 표본에서 원본 ID·표시 정보·이미지·상품 관계를 대조합니다.
- 추가 페이지 확인과 실제 확보 수량 대조로 전체 구성 여부를 판단합니다.
- 긴 숫자/선행 0 ID 보존, 복수 카드 분류, 감독 수 별도 집계와 미확인 값 구분을 확인합니다.
- 반복 HTTP 200과 실제 신규 자료·조건 변경 반영 증거를 구분합니다.

### 완료조건

필수 필드의 확보/미확인, 현행·과거 수집 범위, 전체성 확인 방법과 남은 제약이 원문 근거로 정리되어야 합니다. R2가 표본·규모·제약을 바탕으로 기술 구조를 결정할 수 있어야 합니다.

## T003 — R2 데이터·기술 구조 확정

R1의 실측 자료에 맞춰 최소 앱·DB·수집·공개 데이터 구조를 확정하고, R3에서 작은 실제 사례의 전체 흐름을 구현할 수 있게 합니다.

### 순서

1. 실제 선수·출시 카드·카드 개정본·감독·상품·이미지에 내부 ID를 부여하고 외부 ID를 출처·종류·원본 문자열로 보존하는 계약을 정합니다.

5. 새 자료 수집→데이터·관계·이미지 검증→공개 갱신의 흐름을 설계합니다. 재수집·수집 실패·부분 응답에서 정상 데이터와 과거 근거를 보존하는 기준을 정합니다.
6. 앱 빌드·배포 구성, R3 표본 수직 검증과 필요한 검사·테스트를 정의하고 다음 작업 ID를 등록합니다.

### 검증

- 선택: 외부 의존성 없는 Node.js ESM, node:sqlite 기반 빌드 DB와 정적 JSON 검색. 작은 표본의 무료 Pages 배포를 우선하며 추가 API 서버는 현재 불필요합니다.
- 실제 수집 규모 확대 시 JSON 분할·검색 성능·Pages 파일/빌드 한도를 별도 실측합니다. 초기 표본 검증을 50,840개 처리 검증으로 확대하지 않습니다.
- 실제 조사 증거를 정규화한 상품 1개·카드 15개·감독 1명·현재 관측 7개를 validateCatalog로 검증하고 SQLite에 저장했습니다. 실제 선수 식별·전체 구성·상품 감독 연결은 발명하지 않았습니다.
- SQLite 외래키 검사 오류 0건. 동일 표본 재수입은 중복을 만들지 않으며 새 관측은 별도 ID와 개정본으로 보존합니다. 실제 로컬 DB에는 이전 관측·개정 이력도 남아 있습니다.
- 도메인·HTTP 테스트와 실제 정적 빌드가 통과했습니다. ARM64·공개 배포·새 CI DB 이력 복원은 미검증입니다.
- R1의 실제 표본을 계약에 대입해 ID 손실·성급한 병합·복수 분류 손실·불명값의 임의 치환이 없는지 확인합니다.
- 상품의 실제 구성 수량과 모델의 선수/감독/기타 수량이 일치하는지 확인합니다.
- 가격·재화·옵션·제한·시점·조건과 provenance가 구분되어 복원되는지 확인합니다.
- 선택한 기술의 무료 운영 조건·제약과 ARM64 사용 시 호환성을 확인하고 판단 근거를 기록합니다.

## T004 — R3 실제 표본의 DB·검색 전체 흐름 검증

- 단계: R3
- 상태: 완료
- 이전: T003
- 다음: T005

### 목표

검증한 조사 표본을 SQLite와 정적 검색 화면으로 연결하고 부분 확보·미확인·출처를 표시합니다. 이전 감독 관계 필수 기준은 최신 사용자 범위 변경으로 폐기했습니다. 아래 초기 구현 기록과 최종 지원 범위를 구별합니다.

### 초기 순서와 구현 결과 (범위 변경 이전 기록)

1. `npm run data:prepare`로 원본 조사 증거에서 상품 1개·카드 15개·감독 1명을 재현합니다. 내부 ID는 출처·종류·원본 문자열로 결정하고 관측 ID는 시각·응답 해시를 포함해 새 관측과 기존 관측을 구분합니다.
