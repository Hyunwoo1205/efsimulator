# EFHub 전체 누적 수집과 사이트용 추출·검증 계획

> 최신 진행 상태: 대상 Work 채팅에서 players raw는 제작 완료 보고, packs 수집은 **준비 중**이다. 그 채팅의 기존 출력/체크포인트/계획을 먼저 확인해 이어받으며 새 채팅·중복 수집을 만들지 않는다. 준비 상태를 수집 완료로 표시하지 않고 팩 상세/카드 매핑도 별도 검증한다.

T020 최신 사용자 지시에 따라 수집을 두 계층으로 나눈다. **전체 누적 DB/API는 EFHub에서 정상적으로 확보 가능한 모든 players/packs**, **사이트용 DB는 공식 KR 확률표의 현재 유효 판매 회차와 연결 선수 카드**를 대상으로 한다. 전체 누적 범위를 공식 현행 목록으로 제한하지 않는다. 반대로 전체 원본의 모든 카드/팩을 사이트의 활성 목록에 넣지도 않는다.

이번 범위는 점검·계획·인수인계 문서다. EFHub 네트워크 요청·DB 재구축·자동화 활성화·서버/스토리지 생성·푸시/배포는 하지 않는다. 기존 CLI·감사 도구·표본은 보존하며 새 전체 수집기로 자동 승인하지 않는다. 이전 명령·파서·실패 보존 계약은 [이전 구현 기록](reference/COLLECTION_BEFORE_PROBABILITY_SCOPE.md)에 있다.

## 1. 현재 입력 상태와 먼저 할 일

| 입력 | 확인 수준 | 다음 검증 |
| --- | --- | --- |

| 팩 상세와 카드 관계 | 전체 매핑 완료 여부 미확인. 소개 카드 표본/HTML 근거는 전체 manifest가 아님 | 원본 상품/회차ID·카드ID·관계 출처·구성 범위·특수 전체성을 상품별로 확인 |

사용자 제공 파일을 원래 HTTP 본문이라고 자동 간주하지 않는다. 페이지별 원본인지, 메타를 뺀 병합 배열인지, 변환본인지 구분하고 제공자가 보존한 페이지·총계·요청/관측시각·해시·로그를 함께 확인한다. 원래 본문 해시와 현재 파일 해시는 별도다. `2119페이지/50840항목`은 이전 사용자 관측의 기대값일 뿐 새 파일의 실제 전수 확보 수가 아니다. 현재 응답의 실제 메타와 관측 시기를 기준으로 판단한다.

| 순서·작업 | 입력 / 실행 | 산출물과 통과 조건 |
| --- | --- | --- |
| T021 기존 raw 수령·검증 | 다른 Work의 기존 선수 파일부터 위치·크기·SHA256·구조·실제/고유ID·중복·누락·provenance 검사. 팩 raw·상세 매핑은 별도 조사 | 원본을 수정하지 않는 검증 보고. 선수·팩·관계의 실제 확보 범위와 미확인/불완전을 각각 기록 |

| 전체 누적 가공 표본 | 검증한 전체 players/packs raw→공급자 중립ID/필드·개정본·팩/카드 관계 정규화. Standard 등 원본 항목 보존 | 새ID 추가, 기존ID 무삭제, 변경 이력, 원문 참조, 누적 버전. 누락 항목의 자동 삭제 금지. 관계 미확인은 임의 연결하지 않음 |
| 사이트용 현재 대상 추출 | 정상 공식 전체 목록·종료·신선도와 누적 상품 회차 매핑→그 회차의 특수 카드·필수 필드/이미지 검증 | 당시 유효 대상의 사이트 DB/스냅샷, 팩별S/N/가상A 검증과 미확인 목록. 전체 누적 버전과 공식 관측을 고정 참조 |

공식 페이지에는 안정 상품ID·가격·재화·시작·리셋·다회 규칙이 없다. 이름/타입/게시일로 값을 추정하지 않는다. 최초 영입의 N/확률과 계정 잔여 명단을 구분한다. 전체 선수 카탈로그와 특정 팩 구성은 별개이며, 같은 이름·같은 타입·비슷한 출시일만으로 상품에 연결하지 않는다.

## 3. 원문·페이지·ID 검증

- 파일별 원문 바이트/해시·수령시각·출처/관측시각·제공 방식·스키마/변환 이력을 기록한다. 원본은 불변 보존하고 검증/변환 결과를 다른 경로에 쓴다. 인증 헤더·쿠키·토큰을 보고서나 Git에 넣지 않는다.
- 페이지 원본이 있으면 total/page/limit/totalPages/hasMore, 페이지 순서·누락·중복·마지막 페이지·총계 일치와 같은 수집 시점인지 확인한다. 메타가 제거된 병합 배열만 있으면 실제 행/고유ID/필수 필드는 검증할 수 있어도 원출처 전체 페이지 완전성을 새로 입증한 것으로 표시하지 않는다.
- 긴 원본ID·선행0·숫자 원문의 정밀도·모든 필드·배열/null·복수 분류를 보존한다. 원본ID 없는 항목은 격리 검토하고 임의ID로 정상 집계를 맞추지 않는다. 동일 이름의 다른 출시 카드나50,000카드를50,000고유 인물로 혼동하지 않는다.
- 중복/충돌은 별도 보고한다. 이름으로 조용히 합치거나 중복 행을 카드 슬롯 수량으로 세지 않는다. 원본 종류·복수 타입·미확인 값을 보존하고 정규화 규칙·버전을 명시한다.
- 전체 누적에 실명 Standard 카드가 있다면 그 원문/ID를 보존할 수 있다. 해당 카드가 특정 팩에 들어간다는 증거는 별도다. 감독 및 상품↔감독 지원은 일괄 제외하고 일부 팩만 수동 연결하는 정책을 재도입하지 않는다.

## 4. 사이트용 카드·구성과 이미지 검증

사이트 후보는 공식 현재 게재·종료 UTC 전·유효한 수집 신선도를 함께 확인한다. 과거7개 표나 마지막 정상 파일이 있다는 사실만으로 현재 판매/시뮬레이션 가능을 표시하지 않는다. 종료 경과·공식 접근 실패·미게재 재확인 중의 처리와 마지막 정상 자료 보존은 [DATA_LIFECYCLE](DATA_LIFECYCLE.md)을 따른다.

모든 대상 특수 카드에 이름·원본/내부ID·원본 타입/복수 분류·출처 표시OVR/조건·정확한 팩 회차 연결·출처/관측시각을 대조한다. 기본/최대레벨/부스터/자체계산 OVR을 혼합하지 않는다. 소개 카드 그룹만 확보한 것을 모든 특수 카드 확보라고 하지 않는다.

이미지URL이 있다는 것만으로 성공하지 않는다. 사이트 대상 이미지의 실제 응답·MIME/디코딩·허용 저장·저장 후 재읽기·해시·카드 연결을 검증한다. hotlink/캐시/재배포 권리를 따로 남긴다. 전체 카탈로그의 모든 이미지를 즉시 다운로드하라는 요구는 아니며 필요한 검증·저장 범위와 권한/비용을 구분한다. 이번 작업에서는 이미지 요청/다운로드를 수행하지 않는다.

동일 회차의 전체 특수 슬롯S와 공식 초기N을 검증한 뒤만 `A=N−S`를 가상 Standard로 표현한다. 빠진 Highlight·unknown 타입·중복·다른 회차·음수 차이를 익명 슬롯으로 숨기지 않는다. 가상 그룹은 실제 수집 카드/선수ID와 별개이며 전체 카탈로그의 Standard를 임의로 넣지 않는다. 세부 계약은 [ARCHITECTURE](ARCHITECTURE.md), 추첨·연출은 [SIMULATOR_PLAN](SIMULATOR_PLAN.md)을 따른다.

## 5. 정상 접근 제약과 실패 보호

허용된 정상 공개 경로/공급자 문서 또는 사용자가 제공한 정상 raw만 사용한다. 기존403/1010을 사이트 선방문·쿠키/토큰 취득·헤더/UA/IP/프록시 변경으로 우회하지 않고 같은 거부 요청을 반복하지 않는다. 사용자가 보고한 선방문/API 활성화 설명은 여기서 실행·검증하지 않는다. 필요한 정상 export/API·허용 정책은 별도 확인 사항이다.

후속 허용 수집은 요청 예산·단일 동시성·공급자가 허용한 속도·checkpoint/재개를 정한다. 403은 자동 접근 중단/검토, timeout/5xx는 제한된 다음 정규 실행 정책으로 처리한다. 200이라도 HTML오류/빈자료/스키마변경/미완료페이지/급감이면 정상으로 발행하지 않는다. HTTP·MIME·원문 크기/해시·허용 헤더·파서 버전·검증 오류를 기록한다. cf-error-type/cf-error-origin/cf-ray 같은 진단 헤더는 향후 허용 요청에서 보존하며 기존 미보존 값을 새 거부 요청으로 보충하지 않는다.

실패·빈 결과·목록 누락·최신 페이지 창의 이동은 전체 누적 엔티티 삭제 요청이 아니다. 신규/개정 후보는 staging에서 검증하고 각 계층의 마지막 정상 버전·원자적manifest·single-writer·백업을 보존한다. fresh 환경 재빌드가 최신 일부 창만으로 누적 이력을 축소하지 않는지도 검증한다. 사이트의 활성 제외와 공용 이미지 캐시 정리는 원본/누적 DB 삭제와 별개다.

## 6. 기존 도구의 용도와 경계

[오프라인 병합 도구](RAW_PAGE_MERGE.md)는 직접 받은 raw page JSON의 바깥 players/packs 래퍼·페이지 메타만 제거하고 내부 항목 원문을 배열로 합친다. 합성 테스트로 도구를 검증했으며 실제 전체 파일 수령/완전성 검증과 다르다. 이미 다른 Work에서 병합 배열을 만들었다면 입력 형식을 먼저 확인하고 이 도구에 억지로 page wrapper를 만들어 넣지 않는다. 별도 검증 절차를 계획하되 이번에 새 대량 처리 프레임워크를 구현하지 않는다.

로컬의 이전 players 관측은 일부 표본이고, packs 연구 JSON에는2쪽60행의 파싱 응답이 있다. 이를 전체 원문으로 가장하거나 재직렬화 해시를 원래 HTTP 본문 해시로 주장하지 않는다. 사용자 제공 새 raw의 상태는 이 과거 로컬 자료의 한계와 따로 기록한다.

과거 EFHub 소개79카드·별도Yaya4카드, 공식 당시 후보5/미확인2·명시 회차/전체 특수 검증0, T009 미선정은 [실행 결과](sources/API_SELECTION_VALIDATION.md)에 역사적 근거로 남긴다. players limit100 403은 본문/헤더 미보존으로 원인 미확정이며 다른 상품403의 원인으로 전용하지 않는다. `data:prepare`는 기존 저장 표본 재현이고 인터넷 수집·새 전체 누적 편입 명령이 아니다.
