## 2. 제품 목표와 변경하지 않는 데이터 원칙

전체 누적층은 EFHub에서 정상 확보 가능한 모든 선수 카드·팩을 보존한다. 새 원본 ID를 추가하고, 같은 ID의 변경은 새 개정과 관측으로 남긴다. 과거 값과 근거를 보존하며 빈 응답·목록 누락·판매 종료를 엔티티 삭제로 해석하지 않는다. 원문에 있는 Standard 실명 카드·과거 카드·다른 출시 버전도 보존한다. 같은 이름의 다른 카드 ID를 합치지 않는다.

사이트층은 [공식 한국어 확률표](https://efootball-web.konami.net/probability_kr.php)의 최신 정상 목록, 종료 UTC, 관측 신선도, 정확한 회차를 검증한 현재 유효 팩과 해당 카드만 누적층에서 추출한다. 판매 변화로 사이트 활성 목록을 추가·수정·제외할 수 있지만 누적층과 과거 발행본은 보존한다. 두 계층은 확보 범위와 완료율의 분모가 다르다.

- 감독의 별도 수집·활성 연결·검색·시뮬레이션은 일괄 제외한다. 원문 내부의 중첩 필드는 보존한다.
- 구매 즉시 일괄 획득하는 고정 팩은 누적 보존 대상이 될 수 있지만 개봉 시뮬레이터에서 제외한다.
- 같은 회차의 모든 특수 슬롯 `S`와 공식 초기 총원 `N`을 검증하고 나머지가 Standard라는 근거가 있을 때만 익명 그룹 `A=N−S`를 만든다. 특수 누락·unknown 타입·중복·음수 차이는 준비 완료를 차단한다. 실제 선수·카드 ID를 위조하지 않는다.
- 공식 표에 없는 시작일·가격·재화·무료 횟수·다회 할인·제한·복원·리셋 규칙은 추측하지 않는다.
- 데이터·갱신·API 운영 검증 이후 추첨 엔진과 3D를 구현한다. 가상 Standard 모션, 연출 건너뛰기, 동작 줄이기, 키보드·스크린리더, 실패 fallback, 모바일 성능, 자산 권리 검증을 포함한다.

| GitHub 작업 파일 | GitHub를 계속 기준 저장소로 사용 가능 | Sites 제공 소스 저장소로 같은 검증 소스 전달 후 저장 버전·배포. GitHub push만으로 Sites 자동 배포된다고 가정하지 않음 |
| 자체 읽기·쓰기 API | Sites 서버 기능으로 구현 가능 | 공식 Vinext starter의 Worker 서버 경로와 D1 접근으로 이식. 공개 조회와 관리 쓰기 권한 분리 |
| 구조화 누적 DB | D1 후보가 적합한 방향 | 실제 스키마·인덱스·배치 수입·개정 보존·쿼리 한도·백업 실측. 스키마 migration과 대량 seed/backfill 분리 |
| raw·이미지·불변 스냅샷 | R2 후보 | 보존·공개 권리, 비용·접근 정책·참조·해시·복원 확인 후 사용 |
| 자동 갱신 | 별도 writer·스케줄 검증 필요 | Sites 연계 자동화 또는 지원되는 실행 경로, 인증·single-writer·재시도·읽기 검증. 배포가 곧 수집기 가동은 아님 |

권장 진행은 **Sites 정적 검토판 → Sites 서버 API + D1 → 필요한 파일에 R2**다. 최종 앱과 API는 한 Site에서 운영하고 데이터 두 계층은 논리적으로 분리하는 구성을 우선 검토한다. 권한·부하·배포 주기의 독립성이 필요하면 API Site를 분리하되 CORS·서비스 인증·비용을 함께 검증한다. 별도 서버가 데이터 계층 분리의 필수 조건은 아니다.

Sites 서버는 Cloudflare Workers에서 실행된다. 따라서 Pages에서 Sites로 배포·관리 경로가 바뀌어도 Cloudflare 런타임을 전혀 사용하지 않는다는 뜻은 아니다. 스킬 문서상 isolate 메모리는 128MB, 외부 연결은 HTTP 기반이며 raw TCP는 지원하지 않는다. 현재의 `node:sqlite` 로컬 파일과 `node:http` 미리보기 프로세스를 그대로 영속 운영 서버로 올리는 방식은 사용하지 않는다. 기존 SQLite는 오프라인 검증·수입 준비에 재사용할 수 있고, 서버 쿼리는 D1 binding으로 구현한다.

**정적 hosting 설정에는 D1/R2 런타임 binding과 DB migration을 같이 붙일 수 없다.** API를 붙이는 시점에 Worker 빌드로 전환해야 한다. Sites의 공식 `sites()` 빌드 통합과 인증 경로를 유지한다. 스키마 migration은 작고 불변하게 관리하며, 데이터 수입은 인증된 별도 배치 경로에서 멱등 처리한다. 방문자 GET에서 원출처 수집을 시작하지 않는다.

GitHub `origin`은 유지한다. 확인한 Sites 소스 helper는 반환된 저장소 URL로 직접 push하며 영구 remote를 교체하지 않는다. 후속 배포 시 저장소·commit·Sites version·archive·URL 대응을 기록하고 소스 이력이 갈라지면 먼저 조정한다. 기존 별도 Sites 초기 페이지를 복원·수정·삭제하거나 이를 본 앱으로 대체하지 않는다.

이번에 Sites 계정 목록 조회가 성공했고, 로컬 공식 빌드 준비 도구가 실제 `dist`를 정적 형식으로 수락했다. **7파일·215,973 bytes가 모두 바이트 동일하게 보존**됐다. 이 검사는 프로젝트 ID가 없는 로컬 진단 복사본을 사용했으며 Site 등록·credential 발급·소스 push·버전 저장·배포를 수행하지 않았다. `_redirects`와 `_headers`가 파일로 보존된 것과 호스팅에서 같은 의미로 적용되는 것은 다르다. 깊은 주소·새로고침·없는 JSON 404·캐시는 T012에서 확인한다.

Sites 계정별 비용·용량·요청 한도, 실제 D1/R2 생성, 서비스 인증, DB 수입·독립 백업·복구, 실제 배포 성공은 아직 미검증이다. 기존 Cloudflare Free 요금표를 Sites의 무료 보장으로 옮겨 쓰지 않는다. 상세 실행 절차와 검증 출처는 [DEPLOYMENT](DEPLOYMENT.md)에 정리했다.

## 7. 이번 검증과 남은 한계

- npm 설치 확인, 기존 Node 테스트 **224/224**, 표본 재현, 정적 빌드, Pages 호환 7파일 비교 통과. 기존 앱·seed·공개 생성물은 변경 없음.
- 원본 두 파일의 크기·해시·행 수, 팩 9개·카드 79개 관계의 raw ID 참조 확인. 원본 수정·EFHub·이미지 요청 없음.
- 관리 검사 **81파일·23작업·13변경 경로**, 상대 링크 **168개**, 변경 diff 검사를 통과했다. 기존 전수 감사 이력과 이번 영향 파일 검토를 구분한다.
- 저장소 기준은 Node 24.19.0 / npm 11.9.0이다. 이 환경의 실행값은 **Node 24.22.1 / npm 11.9.0**이며 설치 중 엔진 차이 경고가 있었다. 지정 버전 확보 시도는 완료되지 않아 중단했다. 로컬 통과를 정확한 지정 버전 재현이라고 표시하지 않는다. 기준 SHA의 GitHub CI는 저장소의 지정 버전 설정으로 성공했다.
- UI 코드 변경이 없어 새 브라우저 검사는 실행하지 않았다. Sites 원격 배포·라우팅·DB 운영 성공도 아직 주장하지 않는다.

이후 작업은 이 저장소의 `work`에서 T010으로 이어간다. 원본 파일과 과거 관계 자료를 재사용하고, 완료 근거를 갖춘 부분부터 T011로 전달한다.
