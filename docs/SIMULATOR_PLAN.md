# 후속 시뮬레이터·3D 계획

이 문서는 R6의 **T031 제품 설계→T017 최소 추첨판/2D→T018 3D 계획**이다. T030 최신 결정에 따라 API 개발은 T025의 검증된 비공개 전달 범위로 완료하고 향후 오류·운영 관찰은 유지보수한다. 실제 eFsimulator 앱·추첨 엔진·3D는 아직 구현하지 않았으며 이번 문서 점검은 그 구현을 시작하는 작업이 아니다. 과거 R1~R5 전체 역사/전역 데이터 완성·새 API 재구축·공개 API 전환을 모든 제품 설계의 선행 조건으로 다시 요구하지 않는다.

## T031 — 실제 앱의 요구·UI·연동·규칙 설계

`services/catalog-view/`는 데이터 검토 viewer이며 실제 앱의 완료판이 아니다. 다음은 실제 앱의 현재 판매 팩 목록→팩 상세→개봉/잔여 풀→획득 결과/내역 흐름, 선택한 API publication/saleId와 세션 버전 고정, 종료/새 버전/오류 처리, 서버 전용 private API 인증·브라우저 비노출, 익명 Standard와 접근성을 설계하는 작업이다. 기존 web/viewer의 재사용 범위와 실제 앱 소스/브랜치/별도 Site 경계도 설계 때 결정하며 지금 자동으로 브랜치를 바꾸거나 Site를 생성하지 않는다.

API ready와 계획상의 simulation_ready는 구분한다. 시뮬레이션 가능 판단에는 같은 회차의 공식N·전체 특수S·신선도/현재성·해당 모드에 필요한 검증된 추첨 규칙이 필요하다. 지금 API 코드/8필드 계약에 준비도 필드를 추가하는 작업은 아니다. viewer의 카드 등급 sidecar는 대표 이미지 표시용이며 추첨 확률/규칙 근거로 사용하지 않는다.

| 설계 입력 | 처리 원칙 |
| --- | --- |
| 공식 초기N·종료UTC·초기 표시 확률, 검증된 전체 특수S/문자열ID와 A=N−S | 보존된 같은 회차 근거와 최신 API snapshot을 연결해 재사용 |
| 균등/반올림 해석·복원/비복원·잔여 처리·단일/다회·리셋·마지막 수량·횟수 제한 | 필요한 범위의 근거를 별도로 확인하며 초기 표시 확률만으로 전부 검증됐다고 보지 않음 |
| 가격/재화/할인·무료/티켓·플랫폼/지역/계정 자격 | 미확인은0·무료·무제한으로 바꾸지 않음. 비용 미확인은 비용 표시를 보류 |
| 미확인 규칙이 필요한 추첨 모드 | 해당 모드 비활성화/이유 표시를 설계. 모든 목록/상세 UI 설계를 중단하지 않음 |

팩별 추첨 규칙 근거/미확인은 앱 전용 레지스트리로 분리할 계획이며 현재 API 계약을 임의 확장하지 않는다. 규칙 레지스트리와 실제 앱 UX 문서의 경로·역할·우선순위는 후속 작성 시 FILE_SYNC에 등록한다. private API+앱 서버 relay를 재사용할 수 있으므로 API 공개 audience 전환은 제품 설계의 필수 조건이 아니다.

## 전체 목록과 시뮬레이션 대상의 경계

누적 raw는 확보한 원본을 보존하고 현재 가공 API는 공식 게재 이력으로 채택된 팩과 카드를 제공한다. 가공 목록에 존재한다고 개봉 가능한 것은 아니다. 시뮬레이터는 **사이트용 스냅샷에서 최신 정상 한국 공식 확률표·종료 시각·관측 신선도·같은 회차/구성이 검증된 현재 유효 판매 팩**만 대상으로 삼는다. 일시적 빈 목록/읽기 실패는 전체 종료로 바꾸지 않으며, 오래된 스냅샷의 실제 종료 시각을 무시하고 신규 세션을 허용하지 않는다. 활성 대상에서 빠진 팩도 누적 DB에서 삭제하지 않는다.

구매 즉시 구성 전체를 받는 고정 팩은 누적 DB/조회에 남을 수 있지만 코인 결제 여부와 관계없이 개봉 시뮬레이터에서 제외한다. 감독은 기존 통일 정책대로 팩의 지원 구성에서 제외한다. 실제 상품에 감독이 없다는 뜻으로 표시하지 않는다. 누적 원본에 Standard 실명 카드가 있어도 임의로 팩에 넣거나 익명 Standard의 실제 ID로 사용하지 않는다.

## T017 추첨과 기본 연출

입력은 사이트용 발행 manifest가 가리키는 시뮬레이션 준비 검증을 통과한 팩/카드 revision, 공식 초기 수/표시 확률과 별도 검증된 추첨 규칙이다. 대상은 공식 KR 확률표의 해당 유효 회차뿐이다. 전체 누적 최신값을 세션마다 직접 섞지 않는다. 실제 결제·계정 연결·게임 API 조작은 범위에 넣지 않는다.

1. **규칙 확정:** 동일 카드 균등 확률/표시 반올림과 초기/잔여 풀을 구분한다. 복원 여부, 단일/다회, 남은 수보다 많은 요청, 마지막 수량, 리셋 조건, 가격/할인·한도는 근거가 확인된 옵션만 지원한다. 확률표의 “잔여 명단에 따라 변동” 설명만으로 세부 리셋/복원 규칙을 모두 추정하지 않는다. 미확인 규칙이 필요한 모드는 비활성화하고 이유를 표시한다.
2. **추첨 엔진:** UI·애니메이션과 분리하고 테스트에서 난수 주입이 가능하게 만든다. 특정 seed나 동작 타이밍이 희귀 카드 확률을 바꾸지 않게 한다. 비복원 규칙이 확인되면 잔여 슬롯에서 균등 선택하고 선택된 슬롯을 제거한다. 다른 규칙은 별도 명시 계약으로 구현한다.
3. **가상 Standard:** 동일 회차의 공식 초기 `N−검증된 전체 특수 카드 슬롯 수 S`를 익명 그룹으로 저장하고 추첨 시 그룹의 실제 잔여 수를 반영한다. 특수 누락·미확인 타입·중복·회차 혼합·음수 차이가 있으면 생성/준비 완료를 차단한다. 일반 이름과 자체 제작 이미지/연출을 사용한다. 실제 선수 ID/특정 실명 선수처럼 표시하지 않는다. 누적 DB의 실제 Standard 엔티티/확보 카드 수와 가상 그룹을 분리한다. 가상 Standard에도 개봉 모션을 제공한다.
4. **기본 화면:** 초기/잔여 수, 획득 카드·횟수, 확인된 가상 비용, 리셋/초기화, 출처/버전/관찰 시각을 표시한다. 실제 게임 계정의 잔여 수와 연결되지 않는 로컬 시뮬레이션임을 분명히 한다. 새 팩 revision이 나와도 진행 중 세션을 몰래 바꾸지 않는다.
5. **카드 연출:** 검증된 이미지·이름·OVR을 연결하고 특수 카드/익명 Standard 모두 결과에 맞는 모션을 제공한다. 빠른 결과 보기·건너뛰기·음소거·키보드·스크린리더·동작 줄이기를 지원한다. 애니메이션 실패가 추첨 결과/잔여 수를 바꾸지 않게 한다.

검증은 N=1/전부 Standard/전부 특수/가상 수 0/잔여 0/범위 초과/음수·분수 입력/중복 카드/미확인 타입/팩 종료·revision 변경/연속 클릭을 포함한다. 결정적 경계 테스트와 통계적 분포 점검은 구분하며 분포 테스트는 허용 오차/표본 수를 기록한다. 표시 확률 반올림값의 합이 100과 다르다고 원본 확률을 임의 보정하지 않는다. 최소 추첨판을 먼저 사용자에게 보여준 뒤 연출을 확장한다.

## T018 3D 확장과 성능

입력은 T017의 검증된 엔진과 승인된 연출 시안이다. 실제 선수 얼굴·클럽 마크·게임 3D 모델을 사용할 권리가 확인됐다는 가정은 하지 않는다. 자체 제작 또는 허용 라이선스 자산을 우선하고 제작자·출처·라이선스·용량·파일 해시를 자산 목록에 등록한다. 인게임 보호 자산의 무단 추출을 작업에 추가하지 않는다.

1. 단일 기본 모델/공간의 작은 시제품부터 만들고 가상 Standard에도 재사용 가능한 모션을 설계한다. 모델링/리깅/애니메이션과 추첨 로직을 분리한다.
2. 압축 모델/텍스처, LOD, 공용 자산 중복 제거, 지연 로딩, 캐시와 해제 정책을 적용한다. 초기 화면에 모든 팩의 모델을 내려받지 않는다.
3. 대표 저사양 모바일·데스크톱에서 초기 다운로드/첫 결과까지 시간·프레임 시간·메모리·네트워크·기기 발열을 측정해 수용 기준을 정한다. 서버 이전만으로 브라우저 렌더링 문제가 해결된다고 보지 않는다.
4. WebGL 미지원·컨텍스트 손실·이미지/모델 로드 실패·느린 연결·데이터 절약/동작 줄이기에서는 2D 카드/텍스트 결과로 전환한다. 접근성·건너뛰기·이전 결과 복구를 검증한다.
5. [DEPLOYMENT](DEPLOYMENT.md)의 파일 수/단일 파일/저장/대역폭·런타임 한도와 실제 자산 크기를 대조한다. 압축/분할→자산 저장소 분리→필요하면 OCI 순서로 비용·권리·운영 부담을 비교한다. 지금 호스팅을 이전하지 않는다.

완료는 엔진 비회귀·자산 권리/크기·모바일 측정·실패 fallback·접근성·검토용 URL의 사용자 확인 후 판단한다. 시안 검토와 운영 배포 승인은 별도이며, 기반 DB나 API가 불완전하면 해당 팩을 준비 완료로 표시하지 않는다.
