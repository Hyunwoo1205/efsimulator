# API 후보 검증과 선정 계획

> T021 입력 검증 완료: 부모 환경에서 제공된 players와 packs raw의 JSON 내부 무결성을 오프라인으로 검사했다. players는 47,397개 객체/고유 문자열 ID이며 중복·충돌은 0건이다. packs는 1,699개 객체로, 고유 slug 1,699개 중 비어 있지 않은 slug는 1,698개다. 팩 구성 카드 ID/명단이 없어 두 raw만으로 관계를 연결할 수 없다. 원본 페이지 완전성·현재성·권리·이미지 실로드·정상 지속 API 공급 검증을 완료한 뜻은 아니다.

> 현재 위치: R2, 이전 T021 완료 → 현재 T010 예정 → 다음 T011. 양쪽 raw의 제작·내부 검사는 완료됐다. 다음에는 기존 Work의 팩 상세/관계 자료가 있는지 먼저 확인하고, 같은 회차의 카드 ID 매핑 근거를 확보해 수입을 준비한다. 스키마·누적 무삭제 개정 설계와 staging import는 T011에서 진행한다. 새 채팅·중복 수집·전체 재수집을 먼저 시작하지 않는다.

이 문서는 T020의 **전체 누적 DB/API와 사이트용 현행 DB의 2계층 계획**에 T021의 양쪽 raw 검증 결과를 반영했다. 실제 이전/현재/다음 상태는 [WORKPLAN](WORKPLAN.md)을 따른다. T008의 후보 조사와 T009의 실제 관측·팩별 게이트·차단 근거는 [선정 검증 결과](sources/API_SELECTION_VALIDATION.md)에 보존한다. 이번 변경은 문서뿐이며 공급자 연락·계약·새 DB 편입은 실행하지 않았다.

**EFHub를 전체 누적 자료의 우선 공급원으로 가공하려는 사용자 방향을 따른다. 정상 지속 접근·이용/저장/재배포 조건과 상품 구성 완전성까지 통과한 최종 운영 공급 계약은 아직 없다.** 한국 공식 확률표는 사이트용 활성 대상의 기준이며 전체 누적 수집 범위를 제한하지 않는다. PesLig 등 다른 후보는 기존 비교 근거로 보존하고 새 공급자 수집을 시작하지 않는다.

## 최신 공급 범위: 누적 원본과 사이트 발행을 분리

| 계층 | 공급·대상 | 검증과 보존 계약 |
| --- | --- | --- |
| 전체 누적 DB/API | EFHub에서 정상적으로 확보 가능한 모든 players와 packs. 과거·현재, 원본에 존재하는 Standard 카드도 포함 | 원문을 보존하고 공급자·원본 문자열 ID별 신규 엔티티를 추가한다. 재관측 수정은 새 revision/필드 이력으로 보존하며 기존 엔티티·개정을 삭제하거나 빈/실패 응답으로 대체하지 않는다. 출처에서 빠졌다는 이유로 삭제하지 않는다 |
| 사이트용 DB/배포 스냅샷 | 공식 KR 확률표의 최신 정상 관측에 있고 종료 시각이 지나지 않은 선수팩과 그에 대응하는 카드 | 같은 회차/구성·필수 필드·이미지·권리를 검증한 누적 자료에서 추출한다. 판매 변동에 따라 추가·수정·활성 제외가 가능하지만 누적 DB는 보존한다. 관측이 오래되거나 목록/파서 검증이 실패하면 새 활성 판정을 발행하지 않는다 |

전체 카드 목록이 있어도 팩 raw 목록이나 팩↔카드 관계가 완성된 것은 아니다. 전체 누적 자료에 있는 모든 팩을 사이트·시뮬레이터 대상으로 삼지 않는다. 감독은 기존 정책대로 지원 구성에서 제외하고, 구매 즉시 일괄 지급되는 고정 팩은 누적 목록에 보존할 수 있어도 시뮬레이터에서 제외한다. 사이트의 익명 Standard는 실제 누적 Standard 카드와 별도 가상 그룹이다.

다른 Work의 `players_raw.json` v1은 47,397개 객체/고유 문자열 ID·중복 0건과 필수 필드 존재를 확인했고, 팩 검증 시에도 기존 SHA-256 `16b5ac4919480bbbf8e5158946322fac1f406f0d66701c4d52c9274107dc94c4`와 동일함을 재확인했다. 이전 50,840과의 3,443 차이는 사용자 설명상 중복 제거 결과다. 원래 페이지/중복 제거 로그는 재검증하지 않았다는 한계를 유지하고 누락 의심으로 막거나 전체 재수집하지 않는다.

팩 raw는 Library 항목 `libfile_467e20cb94a8819195dba5375e7e013a`의 현재 내용을 materialize해 부모 환경에서 검사했다. 197,874 bytes, SHA-256 `bfe4590cfa5acb18106a98206b9acad71616f2622cf0d44ae3257040a56b97d6`이다. 검색의 version은 null, materialize 응답의 `current_version_number`는 0이므로 팩 v1이라고 부르지 않는다.

- 1,699개 객체의 필드는 `name`, `slug`, `date`, `playerCount`뿐이다. slug는 빈 문자열 1개를 포함해 1,699개가 고유하고, 비어 있지 않은 slug는 1,698개다. 빈 name은 1개, 중복 slug·충돌·JSON 중복 키는 0건이다.
- `date`는 모두 유효한 날짜이고 범위는 2022-04-01~2026-10-26이다. 이 값을 수집 시각이나 판매 중 상태로 대체하지 않는다. `playerCount`는 1~48의 정수이고 합계 12,946은 공급자가 선언한 항목별 수량의 합이다. 전체 추첨 풀·고유 선수 수·실제 팩↔카드 관계 수가 아니다.
- 0부터 세는 index 99의 `name`/`slug`는 `dummy`, `date`는 2026-07-23, `playerCount`는 33이다. placeholder가 의심되므로 원본은 보존하고 정규화·공개 단계의 격리를 검토한다. 빈 값도 원본에서 삭제하지 않고 검토 대상으로 남긴다.
- pack ID·card ID·구성 명단·중첩 배열·팩 이미지가 없어 **players와 packs raw만으로 조인할 수 없다.** 이름이나 수량으로 관계를 추측하지 않는다. 두 배열에는 페이지/커서·출처·수집 시각·total 메타가 없어 페이지 전수 완전성과 현재성은 별도 미검증이다. 이번 검증의 EFHub·이미지 요청은 0건이다.

### 두 계층의 통과 조건

1. **누적 입력:** 원본 파일/버전·크기·SHA-256, 파싱과 원본 ID 정밀도, 실제 행 수/고유 ID·중복·충돌·핵심 필드, 수집 시각과 페이지/총계 증거를 검사한다. 배열만 있고 페이지 메타가 없다면 행 무결성만 판단하며 전수 페이지 완전성은 미확인으로 남긴다.
2. **누적 갱신:** players와 packs 각각의 범위/체크포인트·허용 경로·주기·비용을 정하고 동일 ID·동일 내용은 멱등 처리, 변경 내용은 revision으로 추가한다. 삭제·누락·임시 빈 결과·접근 실패는 삭제 신호가 아니다. 실제 운영 API·자동화는 아직 없다.
3. **사이트 발행:** 아래 G0~G6는 사이트에 반영할 해당 회차의 카드·구성·권리·이미지·가상 슬롯에 적용한다. 누적 전체 원본의 확보/무삭제 검증과 서로 대체하지 않는다. 공식 종료 시각과 신선도 검사도 함께 통과해야 한다.

2026-10-25 15:21 UTC 공식 목록을 재확인하고 저장 자료·공개 조건을 검증했다. 당시 정상 EFHub 상품 요청도 403이었으며 필수 게이트 미충족으로 **T009 차단·미완료**다. 아래 후보표의 과거 200/필드 표본은 현재 접근·권리·완전성 통과가 아니다. 모든 미통과 조건과 재개 자료는 실행 결과 문서/JSON에 기록했다.

## 대상과 판단 기준

이 절의 대상은 **사이트용 활성 스냅샷**이다. 목록과 기존 관측은 [공식 기준표](sources/CURRENT_SHOP_COVERAGE.md)와 [구조화 원문 기준](../data/research/probability-scope-baseline.json)을 따른다. 2026-10-25 13:45 UTC 관측은 7개 명단이며, 현재 목록이나 개수로 고정하지 않는다. 일본어 표·캠페인·특별판·전체 웹상점으로 사이트 모수를 넓히지 않는다. 지역·기기 추가 선택을 대상 확정의 선행 질문으로 되돌리지 않는다. 최신 정상 관측과 `end_at > now`를 함께 확인하고 신선도 허용 범위를 넘은 자료로 판매 중이라고 단정하지 않는다.

- 해당 공식 회차의 **모든 특수 카드**에 출시 카드 ID·수량·타입·상품 연결·이름·이미지·표시 OVR이 필요하다.
- **사이트 시뮬레이션에는 Standard 실명·실제 ID 목록을 요구하지 않는다. 누적 원본에 존재하는 실제 Standard는 그대로 보존한다.** 익명 Standard 모델 방향은 승인됐고 실제 구현은 후속 작업이다. 같은 회차의 공식 초기 수 `N`과 완전한 특수 수량 `S`로 `A=N−S`를 검증한다.
- 특수 종류 누락·unknown 타입·중복·다른 회차 혼합을 Standard 수량으로 숨기지 않는다. 누적 전수 처리와 사이트의 해당 회차 특수 완전성은 별도로 보고한다.
- 공식 표가 제공하지 않는 시작·가격/재화·옵션·리셋·계정 자격을 추정하지 않는다. 출처 표시 OVR은 조건 미확인을 함께 표시할 수 있지만 공식 최대 능력이라고 주장하지 않는다.
- 기존 9개 상품·83개 카드·관측은 보존할 이전 표본이며 새 대상의 완료 수가 아니다. 수명 주기는 [데이터 보존 계획](DATA_LIFECYCLE.md)을 따른다.

근거 표기는 **검증**(실제 응답/코드/행 검사), **선언**(공급자 설명/메타), **미확인**(근거 미확보), **제외**(현재 조건상 자동 공급 불가)로 구분한다. 공개 200은 이용·저장·재배포 허가가 아니다.

## T009 재개 시 수행할 순서 — 과거 계획과 최신 선행 작업

아래는 T008에서 세운 공급 검증 순서이며 T009의 미통과 근거는 그대로다. T021의 양쪽 raw 내부 검사는 완료됐고, 최신 순서는 **T010 기존 팩 상세/관계 자료 확인·회차/card ID 매핑 근거 확보와 수입 준비 → T011 스키마·무삭제 개정 설계 후 staging import → 정상 지속 공급·권한 조건 보강과 사이트 발행 게이트 검증**이다. 원본 재수집이나 거부 요청 재시도를 먼저 실행하지 않는다. 이번 변경은 검증 결과와 계획을 문서에 반영하는 것이며 구현·새 수집은 하지 않는다.

1. **근거 고정:** 공식 기준 JSON·기존 응답/해시·현재 후보표를 읽는다. 상품 대응·특수 집합·필수 필드·이미지·권리·갱신 공백을 상품별로 기록한다. 이미 성공한 raw부터 재사용한다.
2. **권리/정상 경로:** EFHub·PesLig의 이용조건을 먼저 확인한다. 부족하면 PESDATABASE.com/TheWinningXI 등의 명시 허용 feed·샘플·조건을 협의 검토 후보로 남긴다. 이번 계획에서 연락·가입·계약이 실행됐다고 쓰지 않는다.
3. **검증 계약:** 정확히 공개/제공된 경로·쿼리·범위·예산·중단 조건·응답 계약·이미지 저장권한·예상 비용을 정한다. 기존 거부 재시도, endpoint/버전 추측, 키/토큰 취득을 일정에 넣지 않는다.
4. **회차·특수 전체:** 가장 작은 대상 1개부터 공식 회차와 연결하고 모든 특수 종류·카드 ID·수량을 대조한다. 다음에는 당시 KR 대상 각각에 같은 기준을 적용한다. 소개 그룹을 근거 없이 합치지 않는다.

## T010 관계 자료 확인·수입 준비 → T011 스키마·누적 개정·DB 표본

- **T010/R2:** 기존 Work의 출력·체크포인트·팩 상세/관계 자료 존재를 먼저 확인한다. 검증된 회차와 원본 card ID가 연결되는 관계 자료를 확보하고, 제공 raw의 출처/해시·빈 값/placeholder 처리·권리·수입 계약을 준비한다. 이미 있는 두 raw의 전체 재수집이나 이름 추측 조인을 하지 않는다. 관계 자료가 없으면 정확한 공백과 허용된 확보 방법을 기록하며 DB 구현부터 시작하지 않는다.

- T009의 선정 계획에는 당시 모든 대상의 특수 manifest/이미지 전수 검증이 필요하며, 실제 결과는 미통과다. T021의 raw 내부 검사도 그 게이트를 대체하지 않는다. T011은 상품 1개의 정규화 DB 표본·N/S/A·내부 연결을 검증한다. 이후 T014 전체 대상 DB 편입 때 모든 연결의 재검증을 확장한다. 합성 Standard는 실제 확보 카드 수와 분리한다.
- T009의 선정용 probe, T010 정식 수집, T011 정규화/DB 검증, 공개·스케줄 운영을 별도로 기록한다. 새로운 revision의 전수 이미지 검증이 실패하면 그 revision을 발행하지 않고 마지막 정상 자료를 보존한다. 원문 보유만으로 권리가 충족된 것으로 처리하지 않는다.

## 중립 ID·OVR·공급자 대체 계약

- 상품 회차·출시 카드·관측의 내부 ID는 공급자와 독립시킨다. 외부 ID는 `(provider, id_type, original_string)`으로 매핑한다. 기존 ID/URL을 일괄 재발급하지 않고 alias/매핑으로 보존한다.
- 공식 응답 순번은 영구 상품 ID가 아니다. 명시 교차 ID가 없으면 공식 명단/종료·공지/배너와 공급자의 회차·특수 카드 근거로 검증한 관계를 `round_verified`로 기록한다. 이름 유사 `candidate`와 구분한다.
- 이름·같은 숫자 ID·비트마스크만으로 실인물·출시 카드·판본을 합치지 않는다. 같은 사람의 다른 카드가 같은 풀에 있으면 서로 다른 구성일 수 있다.
- OVR은 **값+조건/판본+출처 관측**으로 다룬다. 새 값에 이전 훈련/부스터 조건을 붙이지 않는다. 조건 미확인은 표시하되 공식 최대값·동일 조건 정확성을 주장하지 않는다.
- PesLig/EFHub 83 ID가 겹치지만 OVR 14건과 타입 차이가 있다. `Other Special`·`is_variant`·non-Standard를 공식 특수 분류로 자동 치환하지 않는다.
- 어댑터는 raw 메타/권리 참조, 외부/내부 ID·연결 근거, 필드 provenance·조건, 상품별 범위/특수 완전성, 이미지 저장/검증 결과를 공통 계약으로 반환한다.
- `success`/`partial`/`blocked`/`schema_changed`/`identity_conflict`/`conditions_conflict`/`coverage_shrink`를 구분한다. 빈 응답·403·축소·오래된 관측·충돌이 정상 데이터를 지우거나 되돌리지 못하게 한다.
- 공급자 교체 fixture는 같은 회차 A/B 계약·긴 ID·중복·수량 2·이미지 손상·권리 만료·중단/재실행·멱등성을 포함한다. B는 mock으로 계약을 검사할 수 있으며 실제 B 공급자의 권리/자료/대체 검증은 별도로 표시한다. EFHub CDN을 공유하는 사이트는 독립 이미지 장애 대안으로 세지 않는다.

## 익명 Standard 수량 검증

1. 초기 N과 같은 회차의 **완전한** 특수 수량 S를 확인한 뒤 A를 계산한다. unknown 타입·누락·중복·음수·분수·초기/잔여 혼동은 실패다.
2. S는 검증된 출시 카드별 수량의 합이다. 소개 그룹 중복 노출은 중복 수집인지 확인하고, 실제 관계 수량 2는 보존한다. 이름으로 중복 제거하지 않는다.
3. European Midfielders의 공식 Epic 3+Highlight 8에서 소개 8명만 확보했다고 `150−8=142`를 Standard로 만들지 않는다. 누락 Epic 3를 먼저 검증한다. Magical 소개 11도 회차/특수 전체 검증 전에는 S=11로 확정하지 않는다.
4. N=11 명단에서 같은 회차의 특수 11개가 모두 검증되면 A=0일 수 있다. 숫자 11 일치만으로 완료시키지 않는다.
5. 합성 그룹은 실제 선수/카드·외부 ID·실측 이미지/OVR·‘확보한 실제 카드 수’와 분리한다. 가상 수량·근거·검증 시각을 저장하며 가짜 원본 ID를 만들지 않는다. 연출은 [후속 시뮬레이터 계획](SIMULATOR_PLAN.md)을 따른다.

## 권리·비용·갱신 완료 기록

권리는 데이터와 이미지에 각각 적용한다. 수집/원문 저장·정규화 DB·공개 API/사이트·캐시/재배포·출처 표기·만료/철회 범위를 분리하고 제한을 어댑터 계약에 연결한다. 다른 공급자로 조합해도 빠진 권리를 대신 충족하지 못한다.

비용은 요청량·snapshot/이미지 바이트·변경 빈도·보관/백업·재검증·feed 이용료를 측정한다. 무료 공개 페이지의 무제한 이용을 가정하지 않는다. Pages 우선 배치와 한도·자산 저장소/OCI 비교는 [배포 계획](DEPLOYMENT.md)을 따르며 지금 유료 서비스·인프라 변경을 실행하지 않는다.

최종 선정 기록에는 대상 시점/범위, 역할별 provider, G0~G6 보고서, 미기재 게임 규칙, 허용 요청량·비용, 실제 갱신 근거, 이미지 전수 저장 결과, 장애/교체 한계를 포함한다. 작업마다 [WORKPLAN](WORKPLAN.md)의 이전/현재/다음·추가 조건과 [FILE_SYNC](FILE_SYNC.json)의 관련 파일/우선순위를 갱신한다.
