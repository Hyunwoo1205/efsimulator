# 데이터 갱신·전체 아카이브·자체 API

> T036 자동 갱신의 최신 공통 완료 절차는 [AUTOMATION](AUTOMATION.md)을 따른다. 정상 변경은 비공개 묶음 저장·원격 발행·API/두 소비 사이트 전체 대조·GitHub 요약 영수증/CI 확인까지 수행하고 미완료 단계만 재개한다. 아래 과거 작업의 정기 커밋 금지는 코드/규칙/관리문서에 유지하되 검증 요약 고정 파일은 최신 승인으로 허용한다. 미검토 상품/원본 충돌과 실제 자동 반영 범위를 구분한다.

데이터 형식/수명주기는 T024(2026-10-27)의 계약을 유지하고 개발 상태는 T030의 API 완료 기준을 따른다. [전체 파일/필드 계약](CATALOG_DATA_CONTRACT.md), [현재 작업](WORKPLAN.md), [배포 경계](DEPLOYMENT.md)를 함께 따른다. 이전의 전체 raw 공개 API, 얇은 아카이브, 종료 후 24시간 대기 제안은 대체되었다.

## 범위와 순서

원본은 기존 JSON 형식으로 누적한다. 신규 상품이 공식 KR 확률표와 EFHub 양쪽에서 같은 회차로 확인되어야 HTML 수집을 시작한다. new-players와 필요한 상세 HTML만 읽으며 원본 API를 조회하지 않는다. 기존 raw ID와 순서를 보존하고 신규 ID/slug만 추가하며 선수·팩 raw 로그를 각각 쓴다.

가공 DB는 이 중 공식 게재 상품으로 확정한 팩과 그 선수만 누적한다. 선수는 정확히 지정 8개 필드만 포함한다. 관계는 가공 팩의 members에 저장한다. 팩의 특수 인원과 공식 전체 인원·UTC 종료를 구분하고, 원본 오류는 근거 있는 보정값과 원본값을 함께 둔다.

그 다음 종료된 live 항목을 선수 상세 전체와 함께 archive에 옮기고, 새로 확정한 현재 유효 상품을 가공 DB에서 중첩하여 live에 추가한다. 가공 선수/팩·live·archive가 바뀔 때마다 대상 파일과 ID·전후 수·전이·근거를 API 로그에 남긴다. live와 archive는 가공 팩의 완전한 분할이며, 선수의 중복 제거 합집합이 가공 선수 전체와 같다.

## 실패와 시간

403/429/challenge는 해당 EFHub 수집 실행을 중단한다. 거부 요청을 즉시 반복하거나 헤더·쿠키·프록시·토큰을 바꾸어 우회하지 않는다. 영속 transportState의 nextRequestAt 이전에는 해당 origin 요청을 생략하고, 요청 가능 시 정상 HTML 요청을 수행한다. 실제 연속403/429는2→4→최대8시간 대기와 동일 오류 반복 알림 생략 정책을 따른다. 빈 문서·부분 HTML·파서 오류·시간 초과·2시간보다 오래된 공식 관측은 신규 발행이나 상품 삭제 근거가 아니다.

이미 검증한 UTC 종료 시각은 출처 장애 중에도 적용한다. 종료와 공식 정상 전체 목록의 미게재는 각각 ended와 official_removed로 보존한다. 같은 제목의 종료/인원 변경은 새 검증 후보가 필요하며 이전 회차의 현재성을 추정하지 않는다. 재판매와 같은 회차의 정정을 입증할 수 없으면 자동 합치지 않는다.

예약 실행 사이에 종료가 도래하면 HTTP live 조회는 서버 UTC로 제외하고 archive 조회는 그 전체 자료를 포함한다. GET에서 파일·DB를 수정하지 않는다. 영속 파일 이동과 로그는 다음 갱신에서 확정한다. API ready를 전체 공식 범위 완성으로 표현하지 않는다.

## 원자적 파일과 DB 발행

scripts/lifecycle/workspace.mjs는 raw/processed/live/archive/logs를 불변 versions/<hash>/에 기록한다. 모든 참조·분할·수·파일 해시를 확인한 뒤 CURRENT.json을 원자적으로 바꾼다. 이전 세대와 원본 바이트는 보존한다. 쓰기 잠금과 expectedVersion으로 동시 수정 손실을 방지한다. run-cycle을 실제 호출한 검증 기록과 시간별 경량 사전검사를 구분한다. 양쪽 관련 HTML/데이터와 종료 상태가 같으면 예약 작업은 run-cycle·checks/receipt·SQL·압축·저장·응답 없이 조기 종료한다.

scripts/lifecycle/publication.mjs는 가공 자료만 담은 불변 D1 버전을 만든다. 모든 chunk를 적재하고 실제 DB 레코드와 내용 해시를 비교한 뒤, 이전 활성 버전 조건을 건 단일 포인터 전환을 실행한다. 부분 업로드·내용 충돌·잘못된 참조·오래된 쓰기는 활성화하지 않는다. API는 요청마다 포인터를 한 번 읽고 같은 버전으로만 조회한다. 기존 staging 테이블로 대체 조회하지 않는다.

run-cycle.mjs의 --db는 로컬 SQLite 검증 대상이다. T025의 원격 publication writer/client는 별도의 인증된 고정 JSON 적재·전량 readback·해시 검증·CAS 활성화를 수행한다. 원격 적재/조회/데이터 복구는 실제 검증됐으며 로컬 성공과 구분한 근거는 WORKPLAN T025 및 구조화 배포 기록을 따른다.

## 현재 상태 — T030 API 완료 기준

API 개발은 검증된 private 전달 범위로 완료하고 오류 수정·운영 관찰을 유지보수로 분리한다. T028에서 당시 공식7상품 모두의 전체 특수ID를 연결했고 T025에서7팩70카드·live7/archive0을 실제 D1에 적재해 원격 전체 내용/해시와 API 조회를 검증했다. 이번 상태 점검의 health/manifest도 HTTP200·ready=true·database=connected·같은 publication `c8cbaa7783d2889870347cf1509d3dc3141c41f76db81245c8aadf236e3dd854`를 반환했다. 이 수치는 해당 점검 시점의 관측이며 앞으로의 판매 수나 장기 가용성 보장이 아니다.

기존 hourly 작업의 원격 발행 공통 지침과 fresh 소스/서비스 접근·재실행 검증을 재사용한다. T025 연결 이후 다음 실제 예약 변경 실행, 연속 EFHub 가용성, 브라우저 상호작용 QA와 계정 비용/한도를 이번 문서 정리로 검증 완료 처리하지 않는다. 남은 관찰은 유지보수로 진행하며 다음 실제 앱의 요구·UX·규칙 설계를 API 재구축 단계로 돌리지 않는다. API 공개 전환 없이 앱 서버가 private API를 사용할 수 있다.

## T024 초기 구축 관측 — 당시 이력

아래4팩44카드·미확정3상품·미배포 표현은 T024 당시다. T028의 관계 완성과 T025의 실제 원격 배포/복구로 해당 하위 범위가 진전됐으며 현재 상태는 위 절을 따른다.

raw 47,408선수/1,699팩을 보존했다. 공식 HTML7상품 중 기존 정확한 카드 ID 관계로 확정한 4팩44선수를 가공했고 live4/archive0이다. 실제 로컬 API7경로의 200과 중첩 자료를 확인했다. 미확정3상품은 대기한다. EFHub 수집기 HTML403으로 이번 신규 원본 수집은0건이다. 수집 파서는 합성 HTML 및 저장한 공식 HTML로 검증했으며 실제 EFHub 원문 파싱 성공은 아직 아니다.

매시간 점검 예약은 Asia/Seoul 기준으로 활성화했다. 아직 첫 예약 실행 성공·실제 Site 등록/배포·원격 D1 수입·서비스 인증·비용/백업 복구 검증을 완료하지 않았다. 후속 T025에서 남은 관계와 정상 공급·검토 배포를 확인한다. 시뮬레이터와 3D는 이 데이터/운영 검증 뒤의 작업이다.
