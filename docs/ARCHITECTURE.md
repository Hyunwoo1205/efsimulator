# 확률표 선수팩 DB 구조 계획

이번 문서는 새 R2/T010~T011의 설계 방향이다. **스키마·DB·활성 seed·공개 JSON은 아직 변경하지 않았다.** 이전 Node/SQLite/정적 사이트와 실패 보존 코드는 재사용 후보이며 [기존 구현 계약](reference/ARCHITECTURE_BEFORE_PROBABILITY_SCOPE.md)에 보존한다. 현재9상품83카드는 이전 표본이지 새 공식 대상 완료 수가 아니다.

## 범위와 책임

대상 목록·초기 총원·종료·표시 확률은 [공식 KR 기준표](sources/CURRENT_SHOP_COVERAGE.md), 특수 카드 자료는 [선정된 공급자](API_SELECTION.md)의 근거를 쓴다. 공식 목록과 카드 공급자의 역할을 분리한다. 실명 Standard·감독·웹상점/일괄 팩·다른 버전/전역 인물 DB는 신규 모델의 요구가 아니다. 보존 중인 이전 자료는 별도 legacy 영역으로 두고 새 활성 검색/API에 자동 포함하지 않는다. 실제 분리는 구현 단계에서 수행한다.

외부 수집·정규화·검증·DB 물리 저장·정적/동적 읽기 API·시뮬레이터를 각각 경계로 나눈다. 방문자 API 요청에서 외부 출처를 수집하지 않는다. 공급자가 바뀌어도 화면/API/시뮬레이터가 공급자의 원본 필드명이나 ID 규칙에 직접 의존하지 않게 한다.

## 내부 계약과 최소 테이블

아래 이름은 논리적 설계안이며 실제 SQL은 자료 검증 후 T011에서 확정한다.

| 개체 | 주요 필드와 관계 |
| --- | --- |
| `pack_round` | 공급자 중립 내부ID, 공식 원문 제목/별칭, 최초/최근 관측, 공식 초기 수N, UTC 종료/정밀도, 게재/검증/아카이브 상태, 공개revision |
| `official_observation` | 원문URL·UTC시각·상태·해시·파서버전·행 원문 값·검증 결과. 순번은 해당 응답의 위치만 의미 |
| `card_release` | 내부 출시 카드ID, 이름, 원본 타입과 정규화 복수 분류, 관측별 표시OVR/조건, 이미지 자산 참조. 전체 인물DB/다른버전 연결은 필수 아님 |
| `source_mapping` | 공급자·개체종류·원본ID문자열→내부ID, 매핑 근거/검토 상태/회차. 숫자 변환·이름만 병합 금지 |
| `pack_special_member` | 팩회차↔실제 특수 출시카드, 수량, 관계 관측ID, 특수명단 전체성 검증/버전 |
| `anonymous_standard_group` | 팩revision, `kind=anonymous_standard`, 가상 수A, 생성식/근거. 실제선수/카드/원본ID 컬럼에 가짜 값을 넣지 않음 |
| `image_asset` | 원본URL·허용 저장/재배포 범위·MIME/크기/해시·저장키·실제로드/저장/재읽기 결과·캐시 참조/최종사용 |
| `field_observation` / `revision` | 값·조건·공급자·관찰시각·근거를 함께 보존. 확인값을 null로 덮지 않으며 OVR 조건이 다르면 별도 관측 |
| `publication` / `validation_run` | 현재manifest와 불변version·검증보고·이전정상version·백업 참조, 수집→검증→발행 상태 |

공식 페이지에는 안정 상품ID가 없다. 내부ID는 한번 부여한 불투명 식별자로 유지하고 이름/종료/행순번 결합을 영구ID로 쓰지 않는다. 제목·기간·카드집합은 매칭 단서이며 변경/동명 재출시/모호한 회차는 수동 검토 대기다. 원본ID가 같은 숫자여도 공급자가 다르면 같은 카드라고 확정하지 않는다. 기존 내부ID의 검증된 대응이 있으면 보존하거나 명시적 별칭 매핑을 두고 바뀐 API 때문에 무조건 재발급하지 않는다.

이름·이미지·표시OVR이 사용 정보의 중심이다. 타입/안정ID/상품관계는 특수 구성을 검증하고 중복/잘못된 회차를 막기 위해 필요하다. 가격·재화·추첨 옵션·복원/리셋/제한은 향후 정확한 시뮬레이션의 별도 규칙이며 미확인은null이다. 출처 표시OVR과 자체 계산/최대레벨/부스터 적용값을 혼합하지 않는다.

## 특수 카드 완전성과 가상 Standard

1. 같은 공식 팩 회차의 초기 총원N과 공급자의 해당 회차 관계를 검증한다. 공급자 소개 그룹만 읽고 전체 특수 집합이라고 판정하지 않는다.
2. 모든 비Standard 타입을 조사한다. Epic/ShowTime뿐 아니라 Highlight/Trending 등 해당 회차의 특수 카드를 모두 포함한다. 알 수 없는 타입·분류 충돌·누락 그룹이 하나라도 남으면 전체성을 승인하지 않는다.
3. 원본 문자열 카드ID로 페이지/그룹 중복을 제거한다. API 중복행을 물량으로 세지 않는다. 실제 같은 카드의 복수 슬롯이 존재한다면 별도의 검증된 수량이 필요하다. 그렇지 않은 회차는 카드당1슬롯이라는 근거를 확인한다.
4. 완전성이 확인된 특수 슬롯 수S와 `A=N−S`를 계산한다. N/S의 정수·범위·A≥0·S≤N·중복/unknown0을 검사한다. 나머지가 Standard라는 상품 유형/공식 구성 근거를 남긴다. 차이만 계산해 특수 누락을 숨기지 않는다.
5. A는 수집된 실명 카드와 별도 가상 그룹이다. 팩별 가상 슬롯을 내부 시뮬레이션 인덱스로 펼칠 수 있지만 실제 게임 선수ID·출시카드ID를 위조하지 않는다. 표시도 “가상의 스탠다드 선수”로 구분한다.

`special_manifest_verified`, `placeholder_count_verified`, `required_fields_verified`를 분리한다. 이들이 통과하면 `data_ready`이며, `simulation_ready`에는 최신 게재/기간·검증된 추첨 규칙도 필요하다. 현재 코드의 `complete`에 임의 예외를 추가해 새 완전성으로 바꾸지 않는다. 신규 계약과 마이그레이션을 별도로 검증한다. 불완전 팩은 미확인 사유와 확보 수만 제공하며 시뮬레이션 준비 완료 금지다.

## 수집 검증에서 새 DB까지

API 최종 선정 후 공식 대상의 특수 자료를 staging에 수집한다. 모든 카드별 이름/ID/복수타입/OVR조건/상품관계·이미지 실제로드/디코딩/허용된 저장과 재읽기를 검증한다. 원본 값과 오류 보고를 보존하며 표본 이미지 성공을 전수 성공으로 보고하지 않는다.

검증 보고서를 토대로 중립 스키마를 확정하고 필요하면 선정 API 자료로 새 staging DB를 만든다. 원본 용어가 다르면 어댑터 매핑을 명시한다. 기존 DB/seed/관측·ID는 백업하고 신규/레거시 대응표를 남긴다. 레거시의 범위 밖 개체를 새 활성 데이터에 넣지 않되 원본을 지우지 않는다. 우선 완전한 한 팩으로 표본 DB를 검증한 뒤 사용자 검토를 거쳐 전체 대상으로 materialize한다. 자료 검증과 DB 전체 편입은 별도 단계다.

재구축 완료 조건은 원본→정규화의 카드별 비교, 팩별S/A/N 합계, 참조/이미지 저장 재읽기, NULL/미확인 보존, 동일 입력 멱등성, 실패 복구, 공급자 교체 fixture와 새 환경의 재현이다. staging 검증 실패 시 기존 DB/공개 자료를 바꾸지 않는다. 실행과 버전 발행/아카이브는 [DATA_LIFECYCLE](DATA_LIFECYCLE.md), 검토/운영 전환은 [DEPLOYMENT](DEPLOYMENT.md)를 따른다.
