# 초기 데이터·검색 구조

## 선택과 공개 범위

초기 구성은 Node.js 24.19.0의 내장 기능, 빌드 시 SQLite, 정적 HTML·CSS·JavaScript를 사용합니다. 추가 npm 의존성이나 상시 API 서버 없이 검증한 소형 자료를 Cloudflare Pages에 공개할 수 있습니다. 이는 전체 출처를 수집한 운영 DB가 아니라 실제 출처 표본으로 수집→검증→저장→화면 경로를 검증하는 구조입니다.

현재 출처 목록의 관측 총계와 실제 확보 수량은 `data/catalog.seed.json`의 `coverage`와 작업 계획에서 관리합니다. 카드 목록 총계는 출시 카드 레코드 수이며 실존 선수 수가 아닙니다. 공개 자료에 확보 범위·미확인·누락을 표시하고 출처 총계를 확보 수량으로 표시하지 않습니다. 상품 상세의 카드 미리보기가 게임 내 전체 명단을 뜻한다는 근거가 없으면 `source_listed_player_count`와 `total_player_count`를 구분합니다. 상품과 공식 자료의 ID 대응이 없으면 이름만으로 합치지 않습니다.

최신 사용자 지시에 따라 상품별 감독 관계를 일괄 반환하는 정상 API가 미확보인 현재는 **모든 상품에서 감독을 서비스 지원 범위에서 제외**합니다. 일반 `coaches` 목록 총계 2,012는 감독 목록일 뿐 상품별 포함 관계 API가 아닙니다. 일부 상품만 수동 관계를 허용하던 이전 혼합 정책은 사용하지 않습니다. 이는 사용자에 의한 서비스 범위 변경이며 R3 검증 기준의 임의 면제가 아닙니다. 최신 표본 규모는 seed와 작업 계획을 기준으로 합니다. 원격 CI·branch 미리보기는 검증했고 main 운영 반영은 승인 대기 상태입니다.

개별 기사·스크린샷·상품별 감독 일대일 조사와 추가 감독 수집을 중단합니다. 이전 `source_reported` Mourinho 수동 사례와 독립 Niko 목록·상세 표본은 활성 입력·화면·상품 구성에서 제외합니다. [Mourinho 조사 원본](sources/MOURINHO_PRODUCT_RESEARCH.md)과 기존 관측 파일은 삭제하지 않고 비활성 연구 이력으로 보존하며, 이름만으로 EFHub ID와 병합하지 않습니다.

## 데이터와 관계

`data/catalog.seed.json`은 확인된 관측과 정규화한 소형 입력입니다. 관측은 출처·원본 문자열 ID·URL·시각·HTTP 상태·근거를 보존합니다. 카드는 실제 선수와 별도 식별되며 내부 ID, 출처별 외부 ID, 여러 카드 분류, 이미지 형태, 표시 능력과 조건, 근거가 확인된 다른 버전을 저장합니다. 확인되지 않은 선수 연결은 `person_id: null`로 남깁니다.

현재 활성 상품은 확인한 카드와 기타 구성 대상·수량만 연결합니다. active seed의 `managers`는 빈 배열이고 상품 `entries`에 감독 대상은 없습니다. 독립 감독 목록·상세 UI도 보류합니다. 이 빈 배열은 실제 게임 상품에 감독이 없다는 뜻이 아니라 서비스 지원 범위를 반영합니다. 가격·재화·옵션·제한·기간은 각각 보존하고 미확인은 null 또는 명시적인 unknown입니다. 원본의 `$undefined` 같은 전달용 표시는 값으로 저장하지 않습니다.

구성 완전성은 카드 범위와 상품 전체 범위를 구분합니다. 확인한 카드 수량이 전체 카드 수량과 맞더라도, 지원 범위에서 제외한 감독과 미확인 기타 구성품까지 확인했다고 할 수 없으므로 상품 전체 `complete`로 승격하지 않습니다. 미리보기·대표 목록이나 서비스상 빈 감독 목록을 전체 구성 완료의 근거로 사용하지 않습니다.

상품의 게임 내 유형(`kind`)과 구매 방식(`purchase_mode`)은 구분합니다. `purchase_mode`는 `bundle`(일괄 구매·일괄 지급), `draw`(추첨), 또는 미확인 `null`입니다. 게임 내 팩이라고 확인한 `kind: "pack"`에는 `purchase_mode: "bundle"`이 필요합니다. API의 `/packs` 목록이나 상품 이름만으로 이 유형을 부여하지 않습니다. 출처에 상품 묶음이 존재한다는 사실만으로 게임 내 유형·구매 방식이 입증되지 않으면 각각 미확인으로 유지합니다.

일괄 구매·일괄 지급 팩은 코인을 사용해도 DB·검색에 유지하고 미래 개봉 시뮬레이터에서 제외합니다. 미래 대상은 코인 기반 특수 선수 명단뿐이며, 현재는 시뮬레이터 추첨 방식·연출·구현을 진행하지 않습니다.

활성 구성 관계의 각 `observation_id`는 해당 상품의 정확한 출처·외부 ID를 가진 `product` 상세 관측이어야 합니다. 다른 상품·단순 목록을 관계 근거로 사용할 수 없습니다. `total_player_count`와 구성 완전성에는 같은 상품 상세의 명시적 근거와 해당 완전성의 범위가 필요합니다. 목록의 표시 인원수를 전체 명단으로 승격하지 않으며, 카드 대조 결과를 상품 전체 완료로 표현하지 않습니다. 비활성 수동 감독 연구를 이 관계의 예외 근거로 재채택하지 않습니다.

SQLite에는 출처, 관측, 실제 선수, 카드, 상품, 기타 구성품, 이미지, 외부 ID, 카드 분류·버전, 상품 구성, 필드 근거, 개정본, 수입 이력을 분리해 저장합니다. 스키마에 남아 있는 감독 타입·테이블이 활성 감독 데이터나 화면 지원을 뜻하지는 않습니다. 전체 원본 정규화 값도 JSON으로 함께 보존하여 적용 조건·복수 분류·미확인 상태를 복원합니다. 외부 ID는 TEXT이며 이름이나 숫자 패턴으로 병합하지 않습니다.

## 검증과 공개 갱신

`scripts/catalog.mjs`의 `validateCatalog`는 성공 시 입력을 반환하고 실패 시 `CatalogValidationError`를 던집니다. 존재하지 않는 관계, 원본 ID 손실, 실패한 HTTP 근거, 출처·대상 혼합, 허위 구성 완전성, 출처 총계와 다른 전체 수집 표시를 거부합니다.

API 전체 범위·페이지네이션 검증은 기존 R1/T002·R5의 요구이며 별도 중복 작업으로 분리하지 않습니다. 기존 R4/T005에서 공개 확대 전에 실제 최종 페이지·페이지 누락·중복 ID·실제 확보 수와 응답 총계를 대조합니다. 목록 전체를 확인한 것과 개별 상품의 전체 구성을 확인한 것은 별개이고, 카드 전체 목록을 확인해도 실존 선수 전체를 식별했다고 표시하지 않습니다.

현재 [전체 카드 API 감사 기록](../data/research/card-api-audit.json)은 실제 `https://efhub.com/api/public/players?page=1&limit=100` 첫 요청이 HTTP 403을 반환해 중단된 결과입니다. 확보한 페이지는 0개이고 `complete: false`·`pagination_complete: false`이며 공개 확대 전 선행 검증은 미완료입니다. 응답 총계·최종 페이지·실제 전체 카드 수를 이 실행으로 검증하지 못했습니다. 이 사실을 도구의 한계라고 바꾸거나 모든 API 경로가 차단됐다고 해석하지 않습니다. 추가 수동 감독 조사로 공백을 보완하지 않습니다.

`importCatalog`는 SQLite 트랜잭션으로 현재 자료와 개정 이력을 저장합니다. 같은 입력은 중복 개정본을 만들지 않습니다. 관측 ID의 다른 내용 재사용을 거부하고 기존 관측을 보존합니다. 부분 응답의 대상·관계 손실, 출처 총계 감소, 확인값의 미확인 덮어쓰기는 자동 반영하지 않습니다. 실제 삭제나 총계 감소가 확인되면 별도 조정 절차가 필요하며 현재 작은 사례의 자동 경로로 처리하지 않습니다.

`publishCatalog`는 DB와 JSON을 임시 파일로 검증한 뒤 공개 JSON을 마지막에 교체합니다. `scripts/build.mjs`는 기존 DB 이력을 복사해 검증하고 전체 사이트를 임시 디렉터리에서 생성한 후 교체합니다. 검증·빌드 실패 시 이전 공개 자료와 DB를 유지합니다. 파일시스템의 여러 경로를 동시에 교체하는 분산 트랜잭션은 아니므로 상시 서버의 동시 쓰기는 지원하지 않습니다.

현재 흐름은 저장한 조사 표본을 검증해 다시 빌드하는 수동 갱신입니다. 실시간 수집기나 주기적 갱신이 가동 중인 상태로 표시하지 않습니다. R4의 시험 운영과 R6의 실제 출처 변화 확인은 별도 완료 조건입니다.

SQLite 개정 이력은 같은 `artifacts/catalog.sqlite`를 유지하는 실행에서 누적됩니다. 새 CI 환경에서 현재 seed만 빌드하면 과거 DB가 자동 복원되지는 않습니다. 현재 원본 입력의 변경은 Git 이력으로 추적하며, 지속 운영 전에 검증된 관측·개정본의 영속 저장과 백업 경로를 별도로 구현해야 합니다.

## 실행과 배포

Pages rewrite는 실제 활성 상품·카드의 상세 경로만 생성합니다. 감독 목록·상세는 서비스 지원 범위에서 제외합니다. wildcard로 JSON 오류까지 HTML 200으로 바꾸지 않습니다. 전체 수집으로 확장하기 전에는 Pages의 redirect 수 제한과 라우팅 방식을 재검토해야 합니다.

`npm run build`가 `artifacts/catalog.sqlite`와 `dist/data/catalog.json`, 정적 화면, 직접 주소 규칙을 생성합니다. `dist`와 `artifacts` 자체는 Git에 넣지 않습니다. `npm run dev` 또는 `npm run preview`는 빌드된 `dist`를 로컬에서 제공합니다. 정적 서버는 누락 JSON을 HTML로 바꾸지 않고 404로 반환합니다. Pages에도 최상위 `404.html`과 필요한 앱 경로의 명시적 rewrite를 생성하여 누락 JSON·이미지에 자동 SPA 성공 응답을 주지 않도록 구성합니다. 실제 원격 응답은 배포 후 검증합니다.

기존 Pages 루트 정적 배포와의 임시 호환을 위해 `scripts/export-pages.mjs`가 새 `dist`의 고정 7개 파일만 저장소 루트의 추적 생성물로 내보냅니다. 대상은 `index.html`, `app.js`, `styles.css`, `404.html`, `_headers`, `_redirects`, `data/catalog.json`입니다. `web/*`와 seed가 편집 원본이며, 헤더·주소 규칙은 빌드 정의에서 생성합니다. 루트 사본은 직접 수정하지 않고 FILE_SYNC에 생성 원본·재생성 명령과 함께 등록합니다.

로컬 변경은 `npm run build` → `npm run pages:export` → `npm run pages:check` 순서로 반영합니다. CI는 새 빌드 후 `npm run pages:check`로 바이트 일치만 검사하고, 사본이 누락되거나 오래됐으면 실패합니다. CI에서 내보내기를 먼저 실행해 불일치를 가리지 않습니다. 내보내기는 현재 Pages 대시보드를 읽거나 변경하는 기능이 아닙니다.

최종적으로는 Node 24.19.0·npm 11.9.0에서 `npm ci && npm run build`, 출력 `dist`를 직접 배포하는 구성을 검토합니다. 실제 대시보드 설정 전환·원격 빌드·공개 동작을 확인한 뒤 임시 루트 7개 사본·내보내기 도구·관련 npm/CI 구성과 파일 최신화 목록을 함께 정리합니다. 현재 준비를 실제 설정 변경·공개 배포 검증 완료로 기록하지 않습니다. 구체적 순서와 검증은 [배포 절차](DEPLOYMENT.md)를 따릅니다.

정적 JSON은 초기 표본에 적합합니다. 전체 범위로 확장할 때 JSON 크기·검색 지연·클라이언트 메모리·이미지 요청량과 Pages 한도를 측정해 분할이나 검색 API 필요성을 판단합니다. API·DB가 필요하면 무료 웹/API 호스팅을 우선 검토하고 차선으로 사용자의 OCI Ampere A1 Flex 2 OCPU·12GB RAM을 평가합니다. 이 환경의 실행 검증은 Linux x64이며 OCI 접근·ARM64·백업은 아직 검증하지 않았습니다.

## 누적 카탈로그 보존 기준

추적하는 data/catalog.seed.json은 마지막 정상 누적 카탈로그이며 최신 목록 한 쪽의 대체물이 아닙니다. data:prepare는 기존 누적 자료를 먼저 검증하고 초기 관측·현재 수집 창의 candidate를 근거 시점별로 병합합니다. 새 창에서 상품이 사라져도 이전 상품·카드·이미지·관측을 삭제하지 않습니다. 동일 상품의 실제 구성 축소·원본 식별자 변경·관측 ID 충돌은 별도 검토 없이 자동 반영하지 않습니다.

이 기준은 SQLite가 남아 있는 로컬뿐 아니라 기존 DB가 없는 fresh CI에서도 적용합니다. 같은 입력은 바이트 단위로 멱등이어야 하며 준비 도중 canonical이 외부에서 바뀌면 덮어쓰지 않습니다. 실패는 이전 seed와 공개 파일을 보존합니다. 누적 개체와 관측의 보존이며 전체 SQLite 개정 테이블을 새 CI에서 자동 복원했다는 뜻은 아닙니다. 실제 삭제·지원 범위 변경은 원본·이력을 보존하는 명시적 별도 검토로 처리합니다.

## 출처 접근 회복 전의 운영·복구 설계 범위

단일 writer에서 수집 원본 검증→추적 canonical 병합→SQLite staging→정적 공개물 staging→교체 순서를 사용합니다. 실패하면 정상 canonical·관측·공개 파일을 유지합니다. 체크포인트는 페이지 해시뿐 아니라 요청 로그/횟수·연속 페이지·다음 페이지·상태가 정합해야 네트워크 재개 후보가 됩니다. 403의 blocked 상태는 자동 재시도하지 않습니다.

현재 복구 기준은 Git에 추적된 마지막 정상 canonical과 원문 관측입니다. 이를 임시 검증 환경에 복원해 관계·ID·범위·빌드를 검사하면 현재 상태 DB와 공개 파일을 재생성할 수 있습니다. 전체 과거 SQLite 개정 이력까지 보존하려면 DB 파일의 별도 지속 백업과 실제 복원 시험이 필요합니다. artifacts의 로컬 DB와 scope-change 보존본을 영구 외부 백업이 운영 중인 것으로 표시하지 않습니다.

정기 writer·보관 위치·보존 기간과 무료 한도는 아직 실운영으로 확정하지 않았습니다. 새로운 지속 접근·서비스 권한·비용이 필요하면 대상과 근거를 먼저 제시합니다. 저장 표본의 반복 빌드·mock·CI 성공은 실제 신규 자료 반영 또는 R6 완료 증거가 아닙니다.
