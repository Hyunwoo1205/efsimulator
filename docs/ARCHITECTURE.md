# 누적 원본·가공 API·실제 앱의 구조와 설계 이력

## T030 현재 구현과 다음 제품 설계

최신 사용자는 API 개발을 완료로 두고 향후 오류만 유지보수하기로 했다. 현재 구현은 [데이터 계약](CATALOG_DATA_CONTRACT.md)의 누적 raw·공식 상품 한정 가공 publication·전체 중첩 live/archive다. T023/T024/T027/T028의 계약·수집/검증과 T025의 실제 private Worker/D1 배포·원격 적재/전체 해시·조회·포인터 복구·인증을 재사용한다. 아래 T020~T023의 전체 raw API·미구현 스키마 설명은 당시 설계 이력이며 새로운 API 재구축 지시가 아니다.

| 구성 | 실제 책임/상태 |
| --- | --- |
| 비공개 누적 raw/세대/증거 | 기존 원본 형식·문자열ID·파일 해시·관측·로그를 보존. Git/HTTP API에 원본 전체를 넣지 않음 |
| `services/catalog-api` | 별도 owner-private Worker와 D1. `api_versions/api_records/api_current`의 검증된 가공 버전만 조회. 전체 rows/해시 검증 후 expected-current 전환 |
| `services/catalog-view` | 별도 데이터 검토 viewer와 서버 전용 private API GET relay. 실제 eFsimulator 제품 아님 |
| 실제 eFsimulator 앱 | 다음 T031에서 요구·UX·소스/브랜치/Site 경계·API/세션·추첨 규칙을 설계. 아직 구현하지 않음 |

API ready는 해당 가공 publication의 조회 준비다. 계획 용어 simulation_ready에는 같은 회차의 공식 초기N·완전한 특수S·현재성/신선도·필요한 추첨 규칙 근거가 추가로 필요하다. 이 구분을 지금 API 필드나 코드 계약에 추가하는 작업은 아니다. 초기 표시 확률을 추첨 방식·복원/리셋·가격 규칙 전체의 검증으로 확대하지 않는다. viewer의 Epic/ShowTime 대표 이미지용 등급 sidecar는 표시 metadata이며 추첨 규칙이나 확률 근거가 아니다.

실제 앱은 API를 공개 audience로 바꾸지 않고 서버 relay로 사용할 수 있다. credential은 서버에만 보관하고 GET에서 원출처 수집/쓰기를 수행하지 않는다. 확정되지 않은 가격은 비용 표시를 보류하고, 미확인 추첨 규칙이 필요한 모드만 비활성화하는 설계를 먼저 만든다. API 연속 가용성·다음 예약 실행·브라우저 QA·계정 한도/비용의 남은 관찰은 유지보수로 분리하며 앱 설계의 전역 API 재개발 게이트로 사용하지 않는다.

## T020~T023 설계·이관 이력

아래의 현재 위치·미구현·실행 범위 표현은 해당 작성 당시를 뜻한다. 최신 작업 상태는 위 현재 구현과 ROADMAP/WORKPLAN을 따른다.

> T024 최신 지시(2026-10-27): raw는 기존 형식을 유지하는 누적 원본이며 HTTP 조회에 사용하지 않는다. 가공 선수/팩은 공식 KR와 EFHub에서 같은 상품·회차가 확인된 대상만 누적한다. 선수 8개 필드, 팩의 선수 연결, 전체 중첩 live/archive와 파일별 로그를 구현한다. 과거의 모든 raw 항목 공개 API·얇은 아카이브·24시간 이관 대기는 이 결정으로 대체한다. [현재 데이터 계약](CATALOG_DATA_CONTRACT.md)을 우선한다.


> T023 당시 결정: 앱과 API는 별도 Sites 프로젝트로 배포한다. API 독립 소스·초기 D1 schema·로컬 수입 도구를 services/catalog-api에 준비했다. 최신 입력은 카드 47,408개이며 이전 T021/T022 수치는 이력이다. [API 준비 결과](API_SERVER_PREPARATION.md)를 우선한다. 실제 hosted 배포·현재 판매 projection·live 원자적 발행은 아직 미구현이다.

> T022 이관 확인: 기존 raw 두 파일을 이 Work로 가져와 해시·행 수를 확인했고 기존 9팩·79관계의 ID가 raw에 모두 존재함을 확인했다. 제품 위치는 R2/T010 예정이다. 이후 배포는 Sites를 기본으로 하며 실제 DB·서버·배포는 아직 미구현이다. [이관 결과](MIGRATION_STATUS.md)와 [배포 계획](DEPLOYMENT.md)을 최신 기준으로 읽는다.

> T021 파일 내 검증 완료: 선수 raw는 카드 객체와 고유 문자열 ID가 각각 47,397개이고 중복은 0건이다. 기존 SHA256도 다시 확인했다. 팩 raw는 유효한 배열의 1,699개 객체를 확인했다. 팩의 빈 이름·빈 slug와 placeholder 의심 항목은 원본을 보존하고 정규화·공개 대상에서 격리 검토한다. 두 파일 모두 전체 페이지 확보 여부와 현재성은 별도 미검증이며, 팩↔카드 관계와 이미지 로드도 확인되지 않았다. 원본 변경이나 EFHub·이미지 요청은 하지 않았다.

> T022 당시 위치: R2. 데이터 검사 T021과 관리 이관 T022를 마쳤으며 현재 T010은 기존 Work의 상세·관계 자료를 먼저 확인하고 검증된 팩 회차의 카드 ID manifest를 확보·수입할 준비 단계다. 다음 T011에서 실제 필드를 바탕으로 스키마·ID·개정·무삭제 정책을 확정하고 staging 수입과 현행 표본을 검증한다. 새 채팅이나 중복 수집을 만들지 않으며, 모든 역사 팩의 관계를 최초 DB 설계의 선행 조건으로 요구하지 않는다.

T020 당시 사용자 결정에 따른 설계 이력이다. **이번에는 문서만 수정하며 스키마·DB·수집기·활성 seed·공개 JSON·서버를 구현하거나 교체하지 않는다.** 기존 Node/SQLite/정적 사이트는 재사용 후보이며 [기존 구현 계약](reference/ARCHITECTURE_BEFORE_PROBABILITY_SCOPE.md)을 보존한다. 기존 9개 상품·83개 카드는 이전 표본이고 새 2계층 모델의 완료 수가 아니다. 실제 작업 상태와 다음 순서는 [WORKPLAN](WORKPLAN.md)을 따른다.

## 1. 두 데이터 계층과 책임

| 계층 | 입력·목적 | 포함·변경 정책 |
| --- | --- | --- |
| 전체 누적 DB/API | EFHub에서 정상적으로 확보 가능한 모든 players/packs 원본을 보존·검증·가공하는 공급 계층 | 현행/종료 상품·확보된 출시 카드·원본의 Standard 항목도 포함 가능. 새 ID를 추가하고 기존 엔티티는 삭제하지 않는다. 값이 바뀌면 새 개정본을 추가해 이전 값·원문·근거를 보존한다. 원본에 없는 엔티티를 만들어 전체라고 하지 않는다 |
| 사이트용 DB/배포 스냅샷 | 누적 계층에서 공식 한국어 확률표의 현재 유효 판매 회차와 연결 카드를 추출하는 소비 계층 | 공식 목록·종료 시각·수집 신선도·회차/구성 검증에 따라 추가·수정·활성 제외한다. 종료/대상 제외는 이 계층의 뷰·캐시 변화이며 전체 누적 엔티티 삭제가 아니다 |

전체 누적 계층과 사이트용 계층은 논리적으로 분리한다. 별도 서버·폴더·DB 파일 또는 같은 DB의 별도 테이블/뷰 중 물리 배치는 자료 크기·권한·조회·운영 비용을 검증한 뒤 정한다. 방문자 요청에서 EFHub를 직접 수집하지 않고 사이트는 검증된 자체 API/스냅샷만 읽는다. 전체 원문·정규화 자료의 비공개 저장과 공개 API 제공 권한은 별개로 확인한다.

[공식 한국어 확률표](https://efootball-web.konami.net/probability_kr.php)는 **사이트용 대상 기준**이지 전체 누적 DB의 수집 범위를 제한하는 기준이 아니다. 관측된 7개를 상수로 고정하지 않는다. 원본에 존재하는 일괄 구매·일괄 지급 팩은 전체 누적 계층에서 보존할 수 있지만 개봉 시뮬레이터 대상에서는 제외한다. 감독과 상품↔감독 관계는 지원 범위에서 일괄 제외한다. 실제 상품에 감독이 없다는 뜻은 아니며, 원본 항목에 그와 관련된 필드가 있더라도 raw는 손실 없이 보존한다.

다른 Work에서 제작한 선수·팩 raw는 상위 작업 환경에서 오프라인으로 파일 내 검사를 마쳤다. 선수 raw의 SHA256은 `16b5ac4919480bbbf8e5158946322fac1f406f0d66701c4d52c9274107dc94c4`, 팩 raw의 SHA256은 `bfe4590cfa5acb18106a98206b9acad71616f2622cf0d44ae3257040a56b97d6`다. 파일 내 무결성 검사와 원출처의 전체 페이지·현재성 검증은 구분한다. 선수의 기존 총계와 3,443개 차이는 사용자가 중복 제거 결과라고 설명했으며, 원본 페이지·중복 제거 로그는 재검증하지 않았다. 상세 수치와 입력 식별자는 [COLLECTION](COLLECTION.md)을 따른다.

팩 raw의 실제 필드는 `name`, `slug`, `date`, `playerCount` 네 개뿐이다. `slug`는 원문 키 후보이며 게임의 안정 상품 ID로 단정하지 않는다. `date`도 수집 시각으로 해석하지 않는다. 팩 ID·카드 ID·선수 명단·중첩 배열·팩 이미지가 없어 두 raw를 직접 조인할 수 없다. 이름이나 `playerCount`만으로 관계를 추측하지 않는다. 유효한 팩 회차와 카드 ID manifest를 연결할 근거가 필요하지만, 역사 팩 전체의 관계가 없어도 검증된 범위에서 논리 스키마와 staging 표본을 설계할 수 있다.

빈 이름 1개·빈 slug 1개와 0 기준 인덱스 99의 `name=slug=dummy`, `date=2026-07-23`, `playerCount=33` 항목은 원본을 삭제하지 않는다. 식별·정규화·공개 전에 격리 검토하고 원인과 판정을 남긴다. `playerCount` 합계 12,946은 원문 필드의 선언 합계일 뿐 연결 관계·고유 선수 수·공식 초기 풀 수의 증거가 아니다.

## 2. 공급자 중립 계약과 논리 개체

아래 이름은 **미구현 논리 설계안**이다. 실제 SQL과 API 경로는 검증된 원본을 바탕으로 후속 DB 설계에서 확정한다. 공급자의 원본 필드명이나 숫자 ID 규칙을 화면·시뮬레이터 계약으로 그대로 쓰지 않는다.

| 계층·개체 | 주요 필드와 관계 |
| --- | --- |
| 공통 `source_snapshot` / `source_observation` | 출처·입력 파일 또는 요청의 식별 정보·관측 UTC·원본 바이트 수·해시·파서 버전·기대 총계·실제 총계·검증 보고. 사용자가 준 병합 배열과 원래 HTTP 응답의 provenance를 구분 |
| 전체 `catalog_card` / `catalog_pack` | 공급자 중립 내부 ID, 등록 시각·최근 관측 시각, 현재 검증 개정본 참조. 누적 레지스트리의 엔티티를 수집 누락/종료로 삭제하지 않음 |
| 전체 `entity_revision` / `field_observation` | 원본 값·조건·출처·원문 참조·검증·유효 시각. 새 개정본을 추가하고 이전 값 보존. 동일 내용의 재관측은 관측만 추가해 중복 개정본 방지 |
| 전체 `source_mapping` | 공급자·개체 종류·검증된 원본 키→내부 ID, 매핑 근거·검토 상태. 선수 문자열 ID와 팩 slug를 구분하고 팩의 게임 ID를 지어내지 않음. 긴 ID·선행 0 보존, 이름만 병합 금지 |
| 전체 `pack_card_membership_revision` | 팩의 원본 회차↔출시 카드·수량·관측/개정본·구성 범위·완전성. 소개 카드와 실제 전체 구성/특수 manifest를 구분하고 관계 이력도 보존 |
| 공통 `image_asset` | URL·허용 조회/저장/재배포 범위·MIME/크기/해시·저장 키·실제 로드/디코딩/저장/재읽기·참조/최종 사용. 전체 누적 카드가 있다고 모든 이미지 파일을 즉시 저장하는 것은 아님 |
| 사이트 `official_pack_round` / `official_observation` | 공식 제목/별칭·초기 수 N·UTC 종료·관측 시각/해시·내부 회차 ID·누적 상품 매핑 근거·게재/검증/신선도 상태 |
| 사이트 `site_pack` / `site_pack_member` | 선택한 누적 개정본·현재 대상 자격·확인된 특수 카드 연결·필수 필드/이미지 검증·원본 누적 버전 참조 |
| 사이트 `anonymous_standard_group` | 팩 revision, `kind=anonymous_standard`, 검증한 가상 수 A·N/S/생성식/근거. 실제 선수·카드·원본 ID에 가짜 값을 넣지 않음 |
| 각 계층 `publication` / `validation_run` | 불변 버전·검증 보고·파일 해시·직전 정상 버전·manifest. 전체 누적 버전과 사이트 스냅샷 버전·발행 주기를 분리 |

원본 ID는 공급자·개체 종류와 함께 문자열로 보존한다. 안전한 정수 범위를 넘는 숫자 원문도 손실 없이 보존하고 파싱 방식과 검증을 기록한다. 같은 이름의 선수·다른 출시 카드·서로 다른 공급자 ID를 자동 병합하지 않는다. 선수 원본 ID 또는 검증된 팩 원본 키가 없거나 충돌하면 raw와 검토 대기 기록을 남긴다. 가짜 게임 ID로 정상 항목 수를 맞추지 않는다.

공식 표에는 안정 상품 ID가 없다. 내부 회차 ID는 한 번 부여한 불투명 식별자로 유지한다. 제목·종료·행 순번 결합을 영구 ID로 삼지 않는다. 동명 재출시·이름 변경·모호한 회차는 자동 병합하지 않고 확인 대기다. 기존 검증된 내부 ID 매핑은 보존하거나 명시적 별칭으로 연결한다.

## 3. 누적 추가와 기존 값 수정

1. 새 원본/병합 배열을 불변 입력으로 등록하고 검증한다. 모든 원문 필드는 보존하며 정규화에서 지원하지 않는 필드도 원문 참조를 유지한다.
2. 신규 원본 ID는 누적 레지스트리에 추가한다. 기존 ID는 의미 있는 필드·관계가 달라졌는지 비교한다.
3. 변경은 새 개정본으로 저장한다. 검증된 최신 참조를 이동할 수 있지만 이전 개정본과 근거를 덮어쓰지 않는다. 값이 없다는 이유로 확인값을 null로 덮지 않으며 OVR 조건이 다르면 별도 관측으로 남긴다.
4. 원본 목록에서 보이지 않는 기존 ID는 `last_seen`과 미관측 상태를 기록한다. 삭제·존재하지 않음·실제 서비스 종료라고 단정하지 않는다. 최신 페이지 창에 없다는 이유로 이전 누적 자료를 축소하지 않는다.
5. 전체 누적 버전의 검증 후에만 사이트용 후보를 만들고, 후보가 참조한 누적/공식 버전을 고정한다. 한 계층의 실패가 다른 계층의 마지막 정상 자료를 훼손하지 않게 한다.

‘추가(삭제x)’는 엔티티와 이력 보존 정책이다. 잘못 읽은 새 값을 활성화하거나 확인된 정정을 영원히 막는 정책은 아니다. 정정은 추적 가능한 새 개정본으로 처리한다. 법적 삭제 의무나 잘못 보관한 비밀 정보는 별도 예외 정책으로 다루며 일반 수집 누락과 혼동하지 않는다.

## 4. 사이트 선택·준비도와 가상 Standard

사이트 대상 자격은 정상 전체 공식 관측의 회차 매핑, 현재 게재 여부, 종료 UTC, 관측 신선도로 판단한다. 페이지에 있었다는 과거 사실만으로 판매 중이라고 표시하지 않는다. 종료 경과·오래된 관측·미게재 재확인 중이면 [수명주기](DATA_LIFECYCLE.md)에 따라 불확실/종료 상태를 구분하고 최신 판매·시뮬레이션 가능을 주장하지 않는다.

사이트의 필수 정보는 이름·이미지·표시 OVR과 그 조건·타입·안정 ID·정확한 상품·회차 관계·출처·관측 시각이다. 가격·재화·추첨 옵션·복원/리셋/제한은 공식 표에 없는 별도 규칙이며 미확인은 null이다. 전체 누적 DB에 Standard 실명 카드가 있더라도 사이트의 익명 Standard 모델을 실명 카드로 자동 대체하거나 해당 팩의 포함 근거로 삼지 않는다.

1. 같은 공식 회차의 초기 총원 N과 누적 상품 관계를 검증한다. 공급자 소개 그룹만 읽고 전체 특수 집합이라고 판정하지 않는다.
2. Epic/ShowTime뿐 아니라 Highlight/Trending 등 해당 회차의 모든 비Standard 특수 종류를 확인한다. unknown 타입·분류 충돌·누락 그룹이 있으면 전체성을 승인하지 않는다.
3. 원본 문자열 출시 카드 ID로 중복을 제거한다. 복수 분류를 별도 카드로 세지 않는다. 동일 카드의 복수 슬롯은 별도 수량 근거가 필요하다.
4. 완전성이 검증된 특수 슬롯 수 S로 `A=N−S`를 계산한다. N·S·A가 범위 안의 정수이고 A가 음수가 아니며 중복·unknown이 각각 0건인지 검사한다. 남은 슬롯이 Standard라는 구성 근거도 확인한다. 특수 누락을 가상 슬롯으로 숨기지 않는다.
5. A는 별도 가상 그룹이며 실제 선수·카드·원본 ID를 위조하지 않는다. 표시도 “가상의 스탠다드 선수”로 구분한다. 실제 생성·추첨·연출은 후속 구현 단계다.

`special_manifest_verified`, `placeholder_count_verified`, `required_fields_verified`, `current_scope_verified`, `freshness_verified`를 나눈다. 카드 데이터 준비와 시뮬레이션 준비를 구분하며 `simulation_ready`에는 검증된 추첨 규칙도 필요하다. 기존 코드의 `complete`를 새 모델 완료로 재해석하지 않는다.

## 5. 후속 구현과 검증

T021 양쪽 raw 수령·파일 내 검사 완료 → T010 기존 Work의 상세·관계 자료 우선 확인과 검증된 팩 회차의 카드 ID manifest 확보·수입 준비 → T011 실제 필드 기반 스키마·ID·개정·무삭제 설계와 staging 수입 → 검증된 현행 표본 순서다. 전체 누적 DB/API와 사이트 스냅샷은 이후 각 단계의 완료 조건에 따라 확장한다. 모든 역사 팩 관계의 확보를 최초 DB 설계의 선행 조건으로 삼지 않는다. 실제 작업 ID별 착수와 배포·운영 선행 조건은 WORKPLAN을 따른다. 기존 DB/seed·관측·ID는 백업하고 새 모델 대응표를 남긴다. 처음부터 삭제하고 다시 채우지 않는다.

검증은 원문 항목과 정규화의 전수 대조, 재실행 멱등성, 신규 ID 추가, 기존 ID 수정/이력 보존, 최신 페이지 창에서 사라진 항목 보존, 긴 ID/선행 0/NULL·복수 타입 보존, 팩·카드 참조, N/S/A, 허용된 이미지 저장 재읽기, 누적·사이트 버전 분리와 실패 복구를 포함한다. 새 환경 재현과 검토용 배포는 별도 게이트다. 이번 문서 갱신이 이를 구현·검증한 것은 아니다.

## 6. Sites 물리 배치 검토

두 데이터 계층의 논리 경계는 유지하고 앱·API는 별도의 Sites 프로젝트로 배포한다. 구조화 누적/개정/관계는 D1, raw·허용 이미지·불변 스냅샷은 필요 시 R2 후보로 둔다. 실제 조회·쓰기·용량·권한·백업·비용 측정 후 배치를 확정한다. 정적 snapshot 검토판은 현행 dist로 시작할 수 있지만 runtime DB binding은 Worker 빌드에서만 사용한다. 로컬 node:sqlite는 오프라인 검증/수입 준비에 재사용하고 hosted 쿼리는 D1 접근으로 구현한다. schema-only migration과 대량 수입을 분리한다. T020 당시에는 해당 schema/API/hosting manifest를 생성하지 않았으며, 이후 실제 구현/배포는 위 T025 기반으로 전달됐다.
